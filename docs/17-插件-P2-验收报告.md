# 插件 P2 验收报告：装载与握手

> 日期：2026-10-23
> 范围：`crates/plugin`（新增：`loader` 子进程与帧协议、`host` 装载状态机与自动重启）、`crates/core/src/plugin_api.rs`（`load` / `unload` / `reload` 真实现 + 崩溃巡检）、`crates/protocol`（`PluginSummary.restarts`）、`apps/desktop`（`policy.ts` 三项放行 + 面板加载/停止/重载）、验收测试与文档同步
> 结论：P2 三个切片（内核装载与握手 → 外壳接线 → 崩溃自动重启与强杀验收）已落地并提交（`7259d96` / `23ff19e` / `1b06006` / `4e44f0a`）。docs/14 §13 给 P2 定的三条判定均达成——**握手不一致拒载**（`6106`，且不留半个装载态）、**崩溃后工具下架**（立即摘表，`6102` 与"不存在"分开）、**Core 退出无孤儿进程**（优雅退出与 `taskkill /F` 强杀两条路径各有一条用例，后者只可能由 Job Object `KILL_ON_JOB_CLOSE` 造成）。能力清单仍为 **71 项**，`plugin.call` / `grant` / `revoke` 仍留在 `6101` 空分支（P3 / P4）。

## 一、交付物

### 1.1 切片一：内核装载与握手（`7259d96`）

| 位置 | 内容 |
|---|---|
| `crates/plugin/src/loader.rs`（新增） | 只负责「怎么和插件说话」：spawn 插件入口 → 按行泵 stdin/stdout → 一帧一个 JSON 对象（JSON-RPC 2.0 风格）→ 按 `id` 配对回包。帧上限 `FRAME_LIMIT_BYTES = 1 MiB`，超限终止读取并判协议违约（防一行吃满内存）；每次请求都带超时，超时返回 `RequestError::Timeout`，**绝不无限等**；stderr 只留尾 40 行（`STDERR_TAIL_LINES`）供崩溃诊断，不整段缓存 |
| 同上：关停三级 | `plugin/shutdown`（等 1.5 s）→ 关 stdin（等 `SHUTDOWN_GRACE = 3 s`）→ `kill` → `TerminateJobObject` 清作业内残留。`Child` 被 drop 时也兜一层，调用方漏调 `shutdown` 不留孤儿 |
| 同上：Windows 作业对象 | `windows-sys` 直接调 `OpenProcess(PROCESS_SET_QUOTA \| PROCESS_TERMINATE)` + `SetInformationJobObject` 设 `KILL_ON_JOB_CLOSE` + `AssignProcessToJobObject`。内核被强杀时句柄随进程消失而关闭，整棵作业连坐——这是「kill -9 Core 也不留孤儿」的唯一保证 |
| 同上：`EXITED_REPLY_CODE = -32000` 哨兵 | 请求期间进程死掉，内部以哨兵码上报，`host` 统一折成 `Crashed`。**这是切片三才发现并修掉的缺陷**：此前会落到 `Plugin { code: -32000 }` 分支被当成「插件拒绝握手」这种确定性失败，自动重启永远不会触发 |
| `crates/plugin/src/host.rs`（新增） | 装载状态机：**授权齐备 → 入口 → spawn → 握手 → 校验 `pluginApi` → 校验工具集合与清单一致**，任一环失败都把刚起的进程收掉，绝不留「进程活着但工具没上架」的半装载态。握手方法 `plugin/handshake`，回 `-32601` 时自动退回旧名 `plugin/initialize`（兼容 P1 之前的 demo 包）；握手总预算 `HANDSHAKE_TIMEOUT = 15 s`（含拉起进程）；`load` 幂等（同 id 重复 load 不重复起进程）；`needs_grant` 的插件**在 spawn 之前**就拒绝，一次进程都不产生 |
| 同上：崩溃判定与自动重启 | `Host::auto_restart()`：进程已死先摘表（工具就此下架），再按原 `resume` 重起；同一次装载会话内最多 `MAX_AUTO_RESTARTS = 3` 次。成功回 `Recovered`（工具重新上架）；协议违规 / 握手被拒 / `pluginApi` 不符等**确定性失败回 `Deterministic`，一次都不重试**；试到顶回 `Exhausted`，`last_error` 原文「已达自动重启上限（3 次），不再重启：…」 |
| `crates/plugin/src/lib.rs` | 只再导出 `manifest` / `install` / `host` / `loader`，本 crate 不认识账本、不做授权判定 |

## 二、验收判定对照

| docs/14 §13 P2 判定 | 结果 | 证据 |
|---|---|---|
| 握手不一致拒载 | 达成 | `host_flow::tool_set_mismatch_leaves_nothing_registered`（插件多报/少报工具 → 杀进程、装载表为空）；`plugin_flow::handshake_tool_set_mismatch_is_rejected_with_6106` 断言端到端错误码 `6106`；`host_flow::api_major_mismatch_is_reported` 覆盖 `pluginApi` 不符（`6104`） |
| 崩溃后工具下架 | 达成 | 崩溃判定走 `take_crashed()` 先摘表：工具立刻从装载表消失，`plugin.status` 的 `tools` 同时为空、状态 `crashed`；此后 `plugin.load` 到顶回 `6102` 而不是 `6101`，「没有这个插件」与「插件刚炸了」分得开 |
| Core 退出无孤儿进程 | 达成 | 优雅路径 `core_shutdown_leaves_no_orphan_plugin_process`（断言插件收到 `plugin/shutdown`，证明是优雅关停）；强杀路径 `forced_kill_of_core_leaves_no_orphan_plugin_process`（`taskkill /F` 不加 `/T`，断言内核先死、插件 10 s 内消失、`plugin.closed` 标记**不存在**）。用例里的插件入口挂心跳保活，实测同参数下无定时器的进程会因 stdin EOF 自行退出（`plain_readline_alive_after_eof = False`）、挂定时器的不会（`keepalive_alive_after_eof = True`），因此该用例的「消失」只能由 `KILL_ON_JOB_CLOSE` 造成，排除了假绿 |
| 能力清单不虚报 | 达成 | 仍为 **71 项**；`call` / `grant` / `revoke` 保持 P0 空分支回 `6101`，`DECLARED_NOT_IMPLEMENTED` 仍为空表；外壳白名单同样只放行 7 项，未虚报 |

## 四、已知限制

1. **`call` / `grant` / `revoke` 仍是 `6101` 空分支**，外壳也未放行：模型侧还不能真正执行插件工具，需 P3（工具注入）与 P4（能力授权 + 审计）。P3 与 P4 必须同版本发布（docs/14 §13 的约束不变）。
2. **工具只到「装载表」，未进模型可见的工具注册表**：`plugin.status` 的 `tools` 能列出、崩溃会下架，但 AI 侧尚看不到，属 P3。
3. **自动重启预算是「每次装载」而非「每小时」**：点一次「加载」重新给 3 次预算，反复手动加载仍可绕过；频率限制留给 P4 的审计/配额层，当前不拦。
4. **崩溃检测是「访问时巡检」不是「秒级监听」**：`plugin.list` / `plugin.status` / `load` / `reload` / `unload` 进来时 `sweep_crashed` 巡检一次，无人访问时账本可能短暂停留在 `ready`，但工具已实际下架（装载表为准）。事件推送属 P5。
5. **`.zip` 包仍不支持**（P1 遗留），`PluginInstallParams.path` 的注释与实现偏差未订正——改注释会牵动 ts-rs 导出，需与 `pnpm types:gen` 同提交，留待做 zip 支持时一并处理。
6. **面板无真机点击验收**：插件面板交互只有 vitest 覆盖，未在真实 Electron 窗口人工点击；「任务管理器核对」这一条以自动化用例代替（`taskkill /F` + 进程存活断言更严格）。真机核对应随 M8 的 NSIS 安装包验收一并补。
7. **插件侧只支持 Node 等价实现**：`main` 按 node 脚本拉起，自建发版或 CI 里 node 不在 PATH 时用 `AIIDE_PLUGIN_NODE` 指路；其他语言运行时（Python 等）需插件自带解释器或依赖系统，宿主不内嵌。

## 五、下一步

按 docs/14 §13，下一阶段是 **P3 工具注入**：`PluginTool` 进 `ToolRegistry`、`plugin.call` 真实现、`risk=write` 的审批映射，让模型真正能调用插件工具。P3 落地即可复用 P2 的装载表与帧协议，主要工作在「工具注册 + 参数校验 + 审批」这一层。

同时 M8 的真机 NSIS 安装/卸载验收、M7 的官方 MCP Server 真连、M6 的真窗口终端同屏仍是欠账，需与插件线并行排期。
