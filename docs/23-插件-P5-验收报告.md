## 三、逐条验收

### 3.1 判定一：未订阅插件收不到事件

| 项 | 内容 |
|---|---|
| 实现 | 内核把 `workspace.changed` / `file.saved` / `session.started` / `session.ended` / `plugin.state_changed` 交给宿主，宿主按清单 `subscriptions` 过滤后**只投给命中的插件**；未订阅的插件既不排队也不唤醒进程 |
| 匹配规则 | 精确名或命名空间通配（`workspace.*` / `session.*`）；通配不跨命名空间 |
| 队列约束 | 每插件队列上限 `MAX_QUEUE = 64`，满则丢最早并计数（`dropped`）；`MAX_FILES_PER_EVENT = 512`，同类事件在队列里**合并 `files[]`** 而不是互相顶掉 |
| 防伪造 | `plugin.state_changed` 由宿主生成并盖 `pluginId`；插件自己发 `plugin/event` 一律拒绝，无法伪造他人状态 |
| 证据 | `crates/plugin/src/host.rs`：`publish_reaches_subscriber_only`（未订阅者收不到）、`wildcard_subscription_gets_session_events`、`announce_state_uses_host_side_plugin_id`、`plugin_cannot_emit_plugin_events`；`crates/plugin/src/events.rs`：`subscriptions_match_exactly_or_by_namespace`、`workspace_payload_carries_paths_only`、`workspace_payload_is_capped`、`state_changed_payload_is_host_generated_with_plugin_id`、`workspace_events_merge_file_lists_instead_of_dropping`、`repeated_events_keep_only_the_latest_payload`、`queue_cap_drops_the_oldest_and_counts_it`、`queue_drains_in_order`（共 8 例，另 3 例属切片四） |
| 口径 | 事件只携带**路径与轻量元数据**（`workspace.changed` 只给 `files[]`，不给正文）；正文要读由插件用自己的 `fs.read` 去取，避免事件通道变成绕过能力闸门的旁路 |
| 结论 | **达成** |

### 3.2 判定二：命令执行走同一套闸门

| 项 | 内容 |
|---|---|
| 接线 | `crates/core/src/dispatch.rs` 的 `methods::plugin::COMMAND => plugin_api::command(...)`；方法表由 `crates/protocol/src/methods.rs` 登记为第 11 个 `plugin.*` 方法、全表第 72 个请求方法 |
| 闸门顺序 | ① 参数形状（`-32602`）→ ② 已安装（`6101`）→ ③ 就绪（`6102`）→ ④ 命令归属（`6106`）→ ⑤ 能力（`6103`，按命令 `risk` 需要的档位判，不看清单申请过什么）→ ⑥ 入参 schema（`-32602`）→ ⑦ 路径（`1002` / `1003`，仅声明了 `pathField` 的命令）→ ⑧ 审批（`3001`，只对 `write` / `exec`）→ ⑨ 转发 `plugin/command-invoke`；配额（`6109`）按「单次命令内 `host/*` 调用次数」在宿主侧计，与 `plugin.call` 同口径 |
| 共用而非复制 | `plugin.command` 复用 `plugin.call` 的同一组闸门函数（`gate_installed` / `gate_ready` / `gate_declared`）与同一个 `truncate_content`（`CALL_CONTENT_LIMIT = 64 * 1024`）；`check_command_params` / `check_command` / `command_snapshot` 只是把「归属对象」从工具换成命令，没有第二套判定。因此「闸门被绕过」在结构上不成立：不存在第二条实现路径 |
| `risk` 来源 | 取自清单声明的命令项（`command_snapshot` 返回 `risk / pathField / args schema`），不是运行期插件自报；`write` / `exec` 才审批，`read` 免问 |
| 审计 | kind 为 `audit_kind::PLUGIN_COMMAND = "plugin.command"`（`crates/store/src/model.rs`），动作取自 `plugin_audit::ACTION_COMMAND = "command"`；`target` 记命令名、`path` 只在声明了 `pathField` 时出现、`code` 只在被拒时出现、`risk` 始终带上。与 `plugin.call` **分开记**：命令是用户显式触发，与「模型调工具」是两条排查线 |
| 证据 | `crates/core/src/plugin_api.rs`：`command_params_reject_blank_id_blank_command_and_non_object_args`、`command_gates_report_the_first_failing_step_only`（首个失败步骤即返回）、`command_args_are_validated_against_the_declared_schema`、`command_risk_decides_whether_approval_is_needed`、`command_scope_key_is_narrowed_by_path`；`crates/protocol/src/methods.rs`：`capability_tables_are_disjoint_and_cover_every_request_method`（断言全表 72 个请求方法，消息里写明「P5 切片二补 `plugin.command`」）、`events_are_not_part_of_the_capability_surface`；`crates/core/tests/plugin_flow.rs`：`capabilities_advertise_all_eleven_plugin_methods`；`apps/desktop/src/main/policy.test.ts`：「放行 P5 的插件命令网关」「插件协议方法已全部放行」（后者由 10 改断言为 11） |
| 前端边界 | 渲染层只能发 `plugin.command`（`policy.ts` 的 `RENDERER_ALLOWED` 放行），拿到的是 `id / label / pluginId / risk`，**没有可调用句柄** |
| 结论 | **达成** |

### 3.3 切片三：全局命令面板（FR-1.7）

| 项 | 内容 |
|---|---|
| 注册表 | `command-registry.ts` 是纯逻辑：固定 9 条内置命令（`workspace.open` / `file.save` / `view.explorer` / `view.search` / `view.ai` / `view.git` / `view.plugin` / `view.mcp` / `terminal.toggle`），插件命令拍平为 `plugin:<pluginId>:<name>`，两者同一套模糊匹配（标题前缀优先于子序列、多词按 AND） |
| 分组与导航 | 固定「内置 → 插件」顺序，空组不出现；`↓` / `↑` 越界回绕，查询变化时选中项回首行，空列表返回 `-1` 而非 `NaN` |
| 执行分发 | 内置命令走 store 动作、**不发 IPC**；插件命令只走 `plugin.command`，参数只带 `plugin_id + command`；插件命令行**不挂 `run`**——渲染层没有直接执行路径 |
| 失败体验 | 六个约定错误码（`6101` / `6102` / `6103` / `6106` / `3001` / `6109`）各有专属中文文案且都点明「没执行」；失败**不关浮层**，可就地换一条命令重试；输出被截断时提示里点明「已截断」 |
| 容错 | 单个插件取详情失败只少那一组命令（逐个 `plugin.status`，互不影响）；清单整体拉不回来时保留旧命令并挂一条提示 |
| 证据 | `apps/desktop/src/renderer/src/command-registry.test.ts`（22 例）与 `command-palette-store.test.ts`（14 例）共 36 例，覆盖上述全部行为；组件 `components/CommandPalette.tsx` 负责 `Ctrl/Cmd+Shift+P` 唤出与键盘操作；`apps/desktop/src/main/policy.test.ts` 有「放行 P5 的插件命令网关」 |
| 结论 | **达成**（命令面；Inline Edit / LSP / `search.symbols` 的**执行行为**不在本切片，见 §5.2） |

### 3.7 切片七：外壳插件活动视图

| 项 | 内容 |
|---|---|
| 通道 | `apps/desktop/src/shared/ipc.ts` 定义 `plugin:log` / `plugin:progress` / `plugin:state-changed` 三通道；主进程 `apps/desktop/src/main/index.ts` 转发，preload 暴露 `onPluginLog` / `onPluginProgress` / `onPluginStateChanged`，`App.tsx` 常驻订阅 |
| 归并规则 | `plugin-activity-store.ts` 三类事件混排后**按到达顺序倒序**（靠自增 `seq`，不靠时间戳，同毫秒也稳）；同插件同 `token` 的进度**覆盖同一行**并把该行抬到队首；`token` 为 `null` 时退化为独立行 |
| 上限 | 500 条，超出丢最早并累计被裁条数；`clear` 后计数归零 |
| 状态联动 | `state_changed` 除追加条目外**顺带刷新一次插件清单**（列表不能停在旧状态）；刷新失败不影响该条活动记录 |
| 筛选 | 级别门槛只作用于**日志**，进度与状态始终可见；未知级别按 `info` 归一（内核只透传，不保证枚举） |
| 只读定位 | 纯遥测视图，不提供任何写/控制入口；插件停启仍走 `plugin.load` / `unload` |
| 证据 | `apps/desktop/src/renderer/src/plugin-activity-store.test.ts`（19 例），覆盖倒序、同 `token` 合并、`null` 退化、百分比夹取、500 上限与 `dropped` 计数、状态迁移与清单刷新、级别筛选与开关不影响收集；组件 `components/PluginActivityPanel.tsx`，入口为 `PluginPanel.tsx` 的「活动」开关 |
| 结论 | **达成** |

## 五、闭环记录与已知限制

### 5.1 P5 阶段口径五点（与 `14-插件系统设计.md` §13 一致）

1. `host/progress` 与 `host/log` 的差别是**故意的**：`log` 不要能力、不受配额约束（日志是排障刚需），`progress` 要能力且可被外壳过滤。
2. `plugin.command` 不是协议面之外的旁路，它就是 `plugin.call` 的第二入口，闸门函数被两者共用。
3. 命令面板的「执行」只能走 `plugin.command` IPC；渲染层拿到的是 `id / label / pluginId / risk`，没有可调用句柄。
4. `net.fetch` 与 `llm.chat` 的边界闸门与路径闸门**互斥**（一个方法只有一种边界），因此各自排在第 ③ 道能力闸门之后。
5. 外壳活动视图是**只读遥测**，不做任何写操作入口。

## 六、结论

**P5 已完成，可进入下一阶段。**

- §13 的两条判定均实测达成：未订阅插件收不到事件（含防伪造与队列约束）；命令执行与 `plugin.call` 共用同一套闸门函数，无第二条实现路径。
- 三个新宿主能力（`host/progress` / `host/net.fetch` / `host/llm.chat`）的闸门均在**产生副作用之前**，且都有「未授权先撞 `6103`」的负向用例。
- 门禁全绿：Rust 44 目标 / 1128 passed / 0 failed / 9 ignored（9 例为 `run_command` 子进程夹具），前端 21 文件 / 409 passed / 0 failed，`fmt` / `clippy` / `typecheck` 退出均为 0。
- 遗留与边界共五项：三项（NSIS 真机、Inline Edit / LSP / `search.symbols`、`plugin_flow.rs` 命名）是登记在 §15 的既有遗留，一项是本轮新发现的模块头注释过期，一项是已闭环的测试误导订正；均不影响 P5 判定，其中「NSIS 真机验收」是发布前唯一必须补的硬项。
