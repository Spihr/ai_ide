# 插件 P1 验收报告：清单与安装

> 日期：2026-10-23
> 范围：`crates/plugin`（新增：清单三段校验 + 包复制）、`crates/store`（迁移 `0004_plugin.sql` 与 `repo::plugin`）、`crates/core/src/plugin_api.rs`（`install` / `list` / `status` / `uninstall` 真实现）、`apps/desktop`（`policy.ts` 四项放行 + 插件面板）、质量门禁与文档同步
> 结论：P1 两个切片（内核清单与安装 → 外壳白名单与面板）已落地并提交（`0a73bf7` / `eaaf425`）。docs/14 §13 给 P1 定的两条验收判定均达成——**非法清单六类错误一次报全**（`6107` 顶层码 + `data.details[]` 逐条）、**安装不产生任何进程**（`plugin.load` 等六个入口仍留在空分支上，端到端断言安装期间子进程数为 0）。能力清单保持 **71 项**不变（`plugin.*` 十方法在 P0 已入表），`DECLARED_NOT_IMPLEMENTED` 仍为空表。

## 一、交付物

### 1.1 切片一：内核清单与安装（`0a73bf7`）

| 位置 | 内容 |
|---|---|
| `crates/plugin`（新增 crate，包名 `ai-ide-plugin`） | 不依赖内核的纯校验与包操作层，依赖只有 `ai-ide-protocol` / `serde` / `serde_json` / `tracing`。对外只暴露两件东西：`manifest`（清单结构与三段校验）与 `install`（读包 → 校验 → 复制到 `<data_dir>/plugins/<id>`，以及反向删除） |
| `manifest.rs` | 三段校验按 **形状 → 语义 → 交叉** 顺序执行，**一次收集全部违规**而非首错即停；每条 `Violation { code, path, message }` 里的 `path` 形如 `$.tools[1].name`，外壳可直接定位。覆盖：必填字段与类型、`tools[].parameters` 结构、id 正则 `^[a-z0-9][a-z0-9-]{1,63}$`、semver `x.y.z`、`main` 归一化后不得越出包根（绝对路径 / 盘符 / UNC / `..` 逃逸全部拒绝）、`pluginApi` major 必须等于宿主（`HOST_PLUGIN_API_MAJOR = 1`，minor 高于宿主只降级不拒载）、能力必须落在 `ALLOWED_CAPABILITIES` 白名单内（`shell.exec` 单列在 `DENIED_CAPABILITIES`）、`tools[].risk=write` 必须申请 `fs.write`、插件内工具重名（6107）与撞核心工具名（6108）分开报、`timeoutMs` 夹在 1 s–120 s |
| `install.rs` | `inspect` 只校验不落盘；`install` 校验通过后复制到 `<data_dir>/plugins/<id>`，同 id 复用旧目录并回 `replaced`；`remove_installed` 删目录；`plugins_root` / `installed_dir` 统一路径口径；复制时**拒绝包内符号链接**，防止复制过程跳出包根 |
| `crates/store/migrations/0004_plugin.sql` | `plugin` 账本一表（`id` / `name` / `version` / `description` / `plugin_api` / `main` / `install_dir` / `manifest_json` / `capabilities_json` / `commands_json` / `subscriptions_json` / `tool_count` / `status` / `last_error` / `restarts` / `installed_at` / `updated_at`），`plugin_capability` 一表（`plugin_id` + `capability` 主键、`granted`、`granted_at`，`ON DELETE CASCADE`）。能力**逐项一行**而不是塞进 JSON 列——撤 `fs.write` 不该改写整行，并发也不会互相覆盖 |
| `crates/store/src/repo/plugin.rs` | `save_plugin` / `get_plugin` / `list_plugins` / `count_plugins` / `delete_plugin` / `list_plugin_capabilities` / `granted_capabilities` / `set_plugin_capability` / `refresh_grant_status` / `set_plugin_status` / `bump_plugin_restarts`；`status` 枚举值建表时就定好（`installed` / `needs_grant` / `ready` / `crashed`），P2 不必再来一次 `ALTER TABLE` |
| `crates/core/src/plugin_api.rs` | 四个方法换真实现：`install`（校验 → 复制 → 写账本，回 `PluginInstallResult { plugin, replaced }`）、`list`（读账本按 id 升序）、`status`（账本 + 回读安装目录清单，给出工具 / 命令明细）、`uninstall`（删账本 + 删目录，目录已不在时 `removed_dir=false` 仍算成功）。升级时只保留旧版本已授权的能力位，**新增能力 `granted=0` → 状态回落 `needs_grant`**（docs/14 §5.4 的重授权要求）。参数缺失/空串仍 `-32602`、插件不存在仍 `6101`、清单非法 `6107` + 一次列全 `details[]`、账本/磁盘失败折 `5003`（与会话侧同口径） |

## 四、已知限制

1. **P1 只支持目录包，不支持 `.zip`**。`PluginInstallParams.path` 的文档注释写着「目录或 `.zip`」，实现按目录处理，压缩包要引入解压与 zip-slip 防护，属后续切片。该注释与实现的偏差记录在此，待做 zip 支持时一并订正（改注释会牵动 ts-rs 导出，需与 `pnpm types:gen` 同提交）。
2. **六个方法仍是空分支**（`load` / `unload` / `reload` / `call` / `grant` / `revoke`）：P2 装载握手与 P4 授权面板做完才有真语义。P3 与 P4 必须同版本发布（docs/14 §13 的约束不变）。
3. **工具未注入**：P1 不读插件声明的 `tools` 进注册表，模型还看不到插件工具，需等 P2 握手 + P3 注入。
4. **能力授权只有账本，没有授权 UI**：`plugin_capability` 已被写入并在升级时参与 `needs_grant` 判定，但用户当前无法在界面上勾选授权，P4 补。
5. **无签名校验与来源信任**：安装只保证包内路径不逃逸，不校验发布者身份。供应链防护目前依赖 §5.4 的重授权机制与用户自觉，签名属未决项。
6. **面板无真机点击验收**：插件面板的交互只有 vitest 覆盖，未在真实 Electron 窗口中人工点击；插件侧也还没有专用 e2e 脚本（M8 的 `pnpm e2e:m8` 目前只覆盖到「MCP 面板可进入」，未覆盖插件面板）。

## 五、下一步

按 docs/14 §13 的顺序，下一阶段是 **P2 装载与握手**：`load` / `unload` / `reload` + 子进程监管（`plugin/*` 帧协议、握手工具集合一致性校验、崩溃后工具下架、Core 退出不留孤儿进程）。P2 的验收里有一条需要单独设计：Core 被 `kill -9` 后插件子进程必须随之退出（Windows 上用 Job Object 的 `KILL_ON_JOB_CLOSE` 验证）。
