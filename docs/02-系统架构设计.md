# AI IDE 系统架构设计

> 文档版本：v0.1（待审阅）
> 依赖：`01-需求规格说明.md`

---

## 1. 总体架构

三层解耦结构：**UI 层（Electron Renderer）**、**编排层（Electron Main）**、**内核层（Rust Core）**。

```
┌─────────────────────────────────────────────────────────────┐
│                     Renderer (React + TS)                    │
│  Monaco Editor │ File Tree │ Chat Panel │ Settings │ Terminal│
│  State: Zustand │ UI: Tailwind + Radix │ Build: Vite         │
└───────────────────────────┬─────────────────────────────────┘
                            │ Electron IPC (contextBridge, typed)
┌───────────────────────────▼─────────────────────────────────┐
│                    Main Process (Node + TS)                  │
│  窗口/菜单/生命周期 │ 内核托管(supervisor) │ 安全存储 │ 原生对话框 │
│  文件对话框 │ 自动更新 │ 崩溃上报 │ 权限策略持久化             │
└───────────────────────────┬─────────────────────────────────┘
                            │ JSON-RPC 2.0 over stdio (NDJSON)
┌───────────────────────────▼─────────────────────────────────┐
│                    Core (Rust, tokio)                        │
│  ┌──────────┬──────────┬──────────┬──────────┬───────────┐  │
│  │ Workspace│  Indexer │  Parser  │  LLM Hub │  Agent    │  │
│  │ (fs/git) │ (ignore) │(tree-sit)│(providers│  Runtime  │  │
│  ├──────────┼──────────┼──────────┼──────────┼───────────┤  │
│  │ Terminal │  Search  │   MCP    │  Store   │  Security │  │
│  │(pty)     │ (ripgrep)│  Client  │ (sqlite) │  (paths)  │  │
│  └──────────┴──────────┴──────────┴──────────┴───────────┘  │
└─────────────────────────────────────────────────────────────┘
```

### 为什么是三层而不是两层

| 方案 | 评价 |
|---|---|
| 渲染进程直连 Rust（Node 侧仅转发） | 违反了单一信任边界；密钥与命令执行暴露在 UI 进程 |
| Electron Main 全包（无 Rust） | 索引 10 万文件、PTY、tree-sitter 在 Node 里性能与可控性都差 |
| **三层（选中）** | UI 只管渲染；Main 管生命周期与安全闸门；Rust 管重活与模型 I/O |

## 2. 进程模型与通信

### 2.1 进程清单

| 进程 | 语言 | 职责 | 生命周期 |
|---|---|---|---|
| Renderer | TS/React | 全部 UI | 随窗口 |
| Main | TS/Node | 窗口、菜单、内核监管、密钥、对话框 | 应用级 |
| Core | Rust | 索引、解析、LLM、Agent、PTY、存储 | 应用级（随 Main 启停） |
| PTY 子进程 | OS shell | 用户命令 | 随终端会话 |
| MCP Server 子进程 | 外部 | 外部工具服务 | 按需 |

### 2.2 通信链路

```
Renderer ──(1)──> Main ──(2)──> Core ──(3)──> LLM Provider (HTTPS/SSE)
```

1. **Renderer ↔ Main**：`contextBridge` 暴露类型化 API，仅允许白名单方法；请求/响应走 `ipcRenderer.invoke`，推送走 `ipcRenderer.on`。
2. **Main ↔ Core**：stdin/stdout 上的 **NDJSON（每行一个 JSON-RPC 2.0 消息）**。选 stdio 而非本地 TCP 的理由：天然进程绑定、无端口冲突、无本机其他进程越权访问风险。
3. **Core ↔ Provider**：`reqwest` + SSE 流式解析。

### 2.3 消息类型

| 类型 | 方向 | 说明 |
|---|---|---|
| Request | Main → Core | 带 `id`，需响应 |
| Response | Core → Main | `result` 或 `error` |
| Notification | Core → Main | 无 `id`，单向事件（流式 token、日志、进度） |
| Cancel | Main → Core | 通过 `$/cancelRequest` 中断长任务（LLM 流、Agent 循环） |

### 2.4 内核监管

- Main 启动 Core 子进程（打包后为随包二进制，开发期为 `cargo run`）。
- 心跳：每 5s 一次 `core.ping`，连续 3 次失败判定僵死 → 强杀重启。
- 崩溃恢复：Core 侧关键状态（会话、打开的文件草稿）持久化在 SQLite，重启后由 Main 触发 `session.restore`，UI 不丢上下文。
- 重启退避：1s / 2s / 5s / 10s，超过 5 次弹窗提示并降级为"仅编辑模式"。

```
│  ├─ desktop/                  # Electron 应用
│  │  ├─ src/main/              # 主进程：窗口、菜单、内核监管、IPC 路由
│  │  ├─ src/preload/           # contextBridge 类型化桥
│  │  ├─ src/renderer/          # React UI
│  │  │  ├─ features/editor/    # Monaco 封装、多标签
│  │  │  ├─ features/explorer/  # 文件树
│  │  │  ├─ features/chat/      # 对话面板、消息流、工具卡片
│  │  │  ├─ features/settings/  # Provider / 模型 / 权限配置
│  │  │  ├─ features/terminal/  # xterm.js

│  │  ├─ vite.config.ts
│  │  └─ electron-builder.yml
├─ crates/
│  ├─ core/                     # Rust 内核主 crate（二进制）
│  ├─ protocol/                 # JSON-RPC 协议定义与 DTO（可被测试单独引用）
│  ├─ workspace/                # 文件系统、路径安全、git
│  ├─ indexer/                  # 文件遍历 + 符号索引
│  ├─ llm/                      # Provider 抽象与各协议实现
│  ├─ agent/                    # Agent 循环、工具实现、权限
│  ├─ mcp/                      # MCP 客户端
│  ├─ terminal/                 # PTY
│  └─ store/                    # SQLite 持久化
├─ packages/
│  └─ shared-types/             # TS 侧与 protocol 对齐的类型（由 schema 生成）
├─ scripts/                     # 构建、打包、协议代码生成、E2E
└─ Cargo.toml / package.json / pnpm-workspace.yaml
```

**约定**：`crates/protocol` 是内核与 UI 的**唯一契约来源**（Rust 定义 → 生成 TS 类型 + JSON Schema），防止两端漂移。

## 4. Rust 内核模块设计

### 4.1 模块职责

| 模块 | 关键 crate | 职责 |
|---|---|---|
| `workspace` | `ignore`, `notify`, `git2` | 工作区打开、路径规范化与越界校验、文件读写、文件监听、Git 状态 |
| `indexer` | `rayon`, `walkdir`, `ignore` | 并行遍历、`.gitignore` 规则、文件名/内容倒排索引（初期用内存 + SQLite FTS5） |
| `parser` | `tree-sitter`, `tree-sitter-{ts,py,rs,go}` | 增量语法解析、符号表（函数/类/方法）、按符号取上下文 |
| `search` | `grep` / `regex`, `ignore` | 内容检索，支持正则、大小写、包含/排除 glob |
| `llm` | `reqwest`, `eventsource-stream`, `tiktoken-rs` | Provider 抽象、流式解析、token 计数、重试与限流、错误归一化 |
| `agent` | 自研 | 循环调度、工具注册与分发、权限裁决、diff 生成与应用、撤销栈 |
| `mcp` | `rmcp` 或自研 JSON-RPC | stdio / HTTP(SSE) 传输、工具发现与调用转发 |
| `terminal` | `portable-pty` | PTY 创建、读写、resize、多会话 |
| `store` | `sqlx`(sqlite) | 迁移、会话/消息/Provider/权限/索引持久化 |
| `security` | 自研 | 路径边界、命令黑名单、敏感目录、脱敏 |

### 4.2 并发模型

- 单 `tokio` 多线程运行时。
- **请求处理**：每条 JSON-RPC 请求 spawn 一个 task，带 `CancellationToken`。
- **流式事件**：LLM 流 → `mpsc` channel → 写 stdout 的通知（NDJSON 行原子写入，需 `Mutex` 保护 stdout）。
- **CPU 密集**（索引、tree-sitter）：`rayon` 池，通过 `spawn_blocking` 避免阻塞异步线程。
- **文件监听**：`notify` watcher → 事件去抖（200ms）→ 增量索引更新 → 向 UI 推送 `workspace.changed`。

### 4.3 关键数据结构（协议层）

```
Session        { id, title, workspace_id, created_at, updated_at, model_ref }
Message        { id, session_id, role, content[], tool_calls[], tool_call_id,
                 model_ref, usage, created_at, parent_id }
ModelRef       { provider_id, model_id }
ToolCall       { id, name, arguments(JSON), status, started_at, finished_at }
ToolResult     { tool_call_id, ok, output, error, meta }
Diff           { path, hunks[], original_hash, new_hash }
PermissionRule { tool_pattern, scope(workspace/global), policy(allow/ask/deny) }
```

## 5. 前端模块设计

### 5.1 状态分层

| 层 | 技术 | 内容 |
|---|---|---|
| 服务端状态（来自 Core） | TanStack Query | 会话列表、消息历史、Provider 列表、文件树 |
| 客户端状态 | Zustand | 打开标签、当前选区、面板布局、草稿输入 |
| 编辑器状态 | Monaco Model | 文档内容与 undo 栈（唯一真源，避免双写） |

**原则**：文件内容只有一个真源（Monaco Model），Core 侧持有磁盘真源；保存是 Model → 磁盘的单向写。

### 5.2 关键 UI 区域

```
┌──────┬──────────────────────────┬───────────────┐
│ 活动 │   编辑器区（多标签）      │  对话面板      │
│  栏  ├──────────────────────────┤  ┌─────────┐  │
│      │                          │  │ 消息流   │  │
│ 文件 │                          │  │ 工具卡片 │  │
│ 搜索 │                          │  └─────────┘  │
│ Git  ├──────────────────────────┤  ┌─────────┐  │
│ 设置 │   面板区（终端/问题/输出）│  │ 输入框   │  │
│      │                          │  │ @引用    │  │
└──────┴──────────────────────────┴───────────────┘
```

### 5.3 渲染性能

- 消息流虚拟滚动（`@tanstack/virtual`），长会话不卡。
- 流式 token 用**批量刷新**（每 50ms 或每 32 token 合并一次 setState），避免逐 token 触发 React 重渲染。
- 代码块按需高亮（`shiki` 懒加载 + 仅可见区域）。

## 6. 存储设计

### 6.1 磁盘布局

```
%APPDATA%/ai-ide/
├─ config.toml           # 应用配置（非敏感）
├─ credentials.enc       # 加密后的 Provider 密钥（safeStorage / DPAPI）
├─ data.sqlite           # 会话、消息、用量、权限规则
├─ index/<workspace_hash>.sqlite  # 工作区索引（FTS5）
├─ logs/                 # 结构化日志，按天滚动
└─ cache/                # 模型列表缓存、临时 diff
```

### 6.2 SQLite Schema（核心表）

```sql
-- 会话与消息
CREATE TABLE session (
  id TEXT PRIMARY KEY, title TEXT NOT NULL,
  workspace_path TEXT, created_at INTEGER, updated_at INTEGER
);
CREATE TABLE message (
  id TEXT PRIMARY KEY, session_id TEXT NOT NULL REFERENCES session(id),
  parent_id TEXT, role TEXT NOT NULL, content_json TEXT NOT NULL,
  model_ref_json TEXT, usage_json TEXT, created_at INTEGER
);
CREATE INDEX idx_message_session ON message(session_id, created_at);

-- Provider 与模型（密钥不在此，仅存引用 key_id）
CREATE TABLE provider (
  id TEXT PRIMARY KEY, name TEXT, protocol TEXT, base_url TEXT,
  key_ref TEXT, headers_json TEXT, enabled INTEGER DEFAULT 1
);
CREATE TABLE model (
  id TEXT PRIMARY KEY, provider_id TEXT REFERENCES provider(id),
  model_id TEXT, display_name TEXT, caps_json TEXT, params_json TEXT
);

-- 权限规则
CREATE TABLE permission_rule (
  id TEXT PRIMARY KEY, tool_pattern TEXT, scope TEXT,
  policy TEXT, created_at INTEGER
);

-- 工具调用审计
CREATE TABLE tool_audit (
  id TEXT PRIMARY KEY, session_id TEXT, tool_name TEXT,
  args_json TEXT, result_summary TEXT, status TEXT, duration_ms INTEGER,
  created_at INTEGER
);
```

### 6.3 密钥处理

1. 用户输入 Key → Renderer 经 IPC 传给 Main（内存中）。
2. Main 调用 `safeStorage.encryptString()`（Windows: DPAPI）→ 密文写入 `credentials.enc`。
3. 建立连接时 Main 解密 → 通过 JSON-RPC 传给 Core（仅在进程内存中，不落盘、不写日志）。
4. UI 回显一律脱敏：`sk-****abcd`。

## 7. 关键设计决策（ADR 摘要）

| 编号 | 决策 | 备选 | 理由 |
|---|---|---|---|
| ADR-1 | Core 用独立 Rust 进程 + stdio JSON-RPC | ① napi-rs 原生模块 ② Node 纯实现 | ①崩溃会带崩 Electron、依赖编译复杂；②性能与 PTY/解析能力不足。独立进程可重启、可单测、语言无关 |
| ADR-2 | 传输用 stdio NDJSON 而非本地 HTTP | localhost HTTP/WebSocket | 无端口、无跨进程越权、无需鉴权协议；代价是不便远程调试（用 `--dev-tcp` 开关兜底） |
| ADR-3 | 契约单一来源在 Rust，TS 类型由 schema 生成 | 各自手写 | 避免两端漂移，协议变更可编译期暴露 |
| ADR-4 | 文件内容真源在 Monaco Model | Core 持有真源 | 编辑器输入延迟最短；保存才同步磁盘 |
| ADR-5 | 索引初期用 SQLite FTS5 全文检索 | 向量检索 / Tantivy | FTS5 零额外依赖、够用；向量检索留作 P2 增强 |
| ADR-6 | diff 应用采用"精确串替换 + 上下文校验" | 行号偏移 / 完整文件重写 | 抗模型幻觉，匹配失败即拒绝并回灌错误让模型重试 |
| ADR-7 | 权限策略默认 `ask`，命令类默认 `ask` + 黑名单双保险 | 默认 allow | 安全优先；用户可按工具放宽 |

## 8. 安全模型

```
        信任边界
  ┌──────────────────────────────┐
  │ Renderer（不可信输入：模型输出会被渲染）│
  │  - 无 Node 权限、sandbox=true        │
  │  - 模型输出经 Markdown 安全渲染，禁用脚本 │
  └───────────┬──────────────────┘
              │ 白名单 IPC
  ┌───────────▼──────────────────┐
  │ Main（策略执行点）              │
  │  - 密钥解密与注入               │
  │  - 权限规则裁决（高风险的最终闸门）│
  └───────────┬──────────────────┘
              │ JSON-RPC
  ┌───────────▼──────────────────┐
  │ Core（能力实现点）              │
  │  - 路径规范化 + 工作区边界校验   │
  │  - 命令黑名单 + 超时 + 工作目录约束│
  │  - 敏感路径拒写（.git/.ssh/系统目录）│
  └──────────────────────────────┘
```

**要点**
1. **双闸门**：Main 做策略裁决（是否允许），Core 做能力校验（是否越界），任一不过即拒绝。
2. **模型输出视为不可信**：工具参数一律 schema 校验 + 路径校验；Markdown 渲染禁用 `javascript:` 与内联脚本。
3. **命令执行**：默认在工作区根目录执行，禁用 shell 元字符拼接（`arg` 数组传参而非字符串拼接），黑名单 + 超时（默认 120s，可配）+ 输出截断（默认 64KB）。
4. **审计**：所有工具调用落 `tool_audit` 表，可在 UI 中查阅。
