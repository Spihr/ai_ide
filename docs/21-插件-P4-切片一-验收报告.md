# 插件 P4 切片一验收报告：能力台账（`plugin.grant` / `plugin.revoke`）

> 日期：2026-10-24
> 范围：`crates/core/src/plugin_api.rs`（`plugin.grant` / `plugin.revoke` 由 `6101` 空分支换真实现，业务内核拆成 `grant_capabilities` / `revoke_capabilities`，新增 `tests` 模块 7 例）
> 结论：授权面**已闭环**。`grant` 写 `plugin_capability` 授权位后立刻把授权集灌进 `FsHostApi`，下一次 `host/*` 当场生效；`revoke` 撤位后同样当场回写，插件无需 `reload` 即被 `6103` 拦住；撤掉 `fs.write` / `net.fetch` / `llm.chat` 这类前提能力时连带 `unload`，账本退回 `needs_grant`、工具下架。`plugin.call` 仍是 `6101`（属 P4 网关切片），`host/fs.write` 仍是 `-32601`（属 P4 写侧切片），能力清单仍是 **71 项**。

---

## 一、交付物

### 1.1 分层：协议壳与业务内核分开

| 函数 | 职责 |
|---|---|
| `grant(peer, state, req)` / `revoke(peer, state, req)` | 只做协议面：解析 `params`、校验 `pluginId`、取库，然后把结果或错误写回帧 |
| `grant_capabilities(state, store, plugin_id, wanted) -> Result<PluginSummary, ErrorObject>` | 业务内核，不碰 `Peer` |
| `revoke_capabilities(state, store, plugin_id, wanted) -> Result<(PluginSummary, bool), ErrorObject>` | 同上，多回一个「是否连带卸载」 |

分开的理由是**可测**：`Peer` 只会往 stdout 写帧，单测拿它断言只能截获一段 JSON-RPC 文本；内核函数直接返回 `Result<摘要, 错误对象>`，授权位、状态机迁移、运行态授权集都能用真库（内存 SQLite）断言。

### 1.2 `grant`：两步都不能省

1. **落账本**：逐项 `set_plugin_capability(plugin_id, capability, true)`；`Ok(None)`（写位时记录已被删）折成 `6100`，不静默跳过；
2. **回写运行态**：按账本重算 `granted_capabilities` 再 `set_granted_for`。

第 2 步是 docs/20 §88 点名的坑：`FsHostApi` 的授权集只在 `load_into` / `unload` 刷新，不回写就会出现「账本已授权、运行中的插件仍被 `6103` 挡」。重算而非差分也是有意的——漏算一项就等于白授权。

能力名的折法（`resolve_capabilities`）守住三条：空串拒（`-32602`，写进 SQL 一行都改不到还报成功就是撒谎）、清单外拒（拼错的名字不能被当成「已撤销」）、去重保序。空数组对 `grant` 表示「清单里的全部」，对 `revoke` 表示「没说清楚」，直接 `-32602`。

### 1.3 `revoke`：撤销不 reload，但要连带卸载

| 情形 | 账本 | 运行态 | 返回值 |
|---|---|---|---|
| 撤读类（`fs.read` / `search` / `workspace.info`） | 授权位清零，`ready` → `needs_grant` | 剩余授权集回写，下一次 `host/*` 撞 `6103` | `unloaded=false` |
| 撤关键类（`fs.write` / `net.fetch` / `llm.chat`）且进程在跑 | 同上，退回 `needs_grant` | 先 `unload`（工具下架），再清空授权集 | `unloaded=true` |
| 撤关键类但进程本就没跑 | 同上 | 按剩余集回写 | `unloaded=false`（没什么可卸） |

关键能力的定义写在 `KEY_CAPABILITIES`：写 / 网络 / 外部模型是「工具承诺的前提」，缺了它插件起来也只会一路 `6103`，留着只会让模型陷进「调用→被拒→重试」的循环，所以整个插件下架。`crashed` 状态不因撤销改写——崩溃原因比这次撤销更值得留在面板上。

### 1.4 单测：`plugin_api::tests`（7 例）

| 用例 | 断言 |
|---|---|
| `grant_writes_ledger_and_runtime_grants_without_reload` | 授权前 `6103`；授权后账本与返回值一致、状态回 `Disabled`；再调 `host/fs.read` 撞的是 `1001`（工作区未开）而非 `6103`——**无需 reload 即生效** |
| `revoke_takes_effect_on_next_host_call_without_reload` | 撤 `fs.read`：`unloaded=false`、状态 `NeedsGrant`、下一次 `host/fs.read` 回到 `6103` |
| `revoke_key_capability_flips_ready_plugin_back_to_needs_grant` | 手工把账本置成 `ready` 后撤 `fs.write`：状态退回 `needs_grant`，剩余授权集只剩 `fs.read`；进程本就没起，故 `unloaded=false` |
| `empty_capabilities_mean_all_for_grant_but_are_rejected_for_revoke` | 空数组对 `grant` 是「全部」，对 `revoke` 是 `-32602` |
| `unknown_and_blank_capabilities_are_rejected` | 清单外能力、空串都 `-32602`，且**不留半张授权** |
| `missing_plugin_reports_not_found` | 不存在的插件是 `6100`，不是「授权成功」 |
| `key_capabilities_cover_write_network_and_llm_only` | 关键能力恰好那三个，读类不在其中 |

## 二、已知限制（留给 P4 后续切片）

1. **`plugin.call` 仍是 `6101`**：网关要按账本实时核能力再转发，属 P4 网关切片；
2. **`host/fs.write` 仍是 `-32601`**：写侧要求「双闸门 + 临时文件 rename + 逐次审批」，属 P4 写侧切片。因此「撤销 `fs.write` 后写调用返回 `6103`」目前只能在账本层验，运行态的即时拦截由读侧用例覆盖；
3. **审计未接**：`grant` / `revoke` 本身没落 `audit` 行，P4 审计闭环切片一并做。
