# 插件 P3 验收报告：工具注入与审批映射

> 日期：2026-10-24
> 范围：`crates/plugin/src/host.rs`（新增 `RunningTool` / `tool_catalog` / `call_tool` / `CallError`，提交 `dc7cde6`）、`crates/core/src/plugin_tools.rs`（新增，`PluginToolBridge` 与注入 / 只读名单）、`crates/core/src/agent_api.rs`（`RunCtx.plugins` 与 `inject` / `read_tool_names` 接线）、`crates/core/src/state.rs`（`Host` 改 `Arc<Host>`）、`crates/core/src/lib.rs`、`crates/agent/src/permission.rs`（`extra_read` 只读直通集合）、端到端用例 `crates/core/tests/plugin_tool_flow.rs`
> 结论：docs/14 §13 给 P3 定的三条判定均达成——**模型可调用插件工具**（注册表名 `plugin__<id>__<tool>`，调用真的落到插件子进程，回包真的以工具结果回到模型面前）、**`risk=write` 触发审批**（`risk=read` 免问，`risk=write` 走既有「未登记 → 审批」）、**拒绝后无副作用**（审批被拒时插件一次都没被执行，用例用「被调用才落的标记文件」证明）。能力清单仍为 **71 项**：P3 不新增协议方法，插件工具经 agent 注册表进入模型视野，不经 `plugin.call`。

## 一、交付物

### 1.1 宿主侧：工具目录与调用通道（`dc7cde6`）

| 位置 | 内容 |
|---|---|
| `crates/plugin/src/host.rs`：`RunningTool` | `plugin_id` / `name`（插件内原名）/ `namespaced_name`（`plugin__<id>__<tool>`）/ `description` / `risk` / `parameters`（插件声明的 JSON Schema 原样携带） |
| 同上：`tool_catalog()` | 现场扫装载表，**只收进程还活着**的插件（崩溃即摘，不给幽灵工具），按 `namespaced_name` 稳定排序——注册表与权限名单都直接吃这个顺序，不在调用方二次排序 |
| 同上：`call_tool()` | 走 `plugin/tool-invoke`，参数 `{tool, arguments}`，`CALL_TIMEOUT = 30 s`；取锁只用于克隆 `Arc<PluginProcess>`，`await` 前必定释放，慢插件不阻塞其他调用 |
| 同上：`CallError` | `NotRunning` / `UnknownTool` / `Timeout` / `Exited` / `Plugin` / `Protocol` 六分支 + `Display`，供上层折成工具错误 |
| 同上：单测 3 条 | 未装载 → `NotRunning`、工具不存在 → `UnknownTool`、正常调用拿回包 |

### 1.2 内核侧：注册表注入（`crates/core/src/plugin_tools.rs`，新增）

| 位置 | 内容 |
|---|---|
| `PluginToolBridge` | 一条声明快照 + `Arc<Host>`。`name()` 返回命名空间名（**刻意与插件内原名不同**：注册表按名线性查找、重名静默失效，前缀是唯一防撞车手段）；`parameters()` 原样透传宿主给的 schema，不在这里「补齐 / 精简」；说明统一加「来源：插件 `<id>`」前缀，模型据此区分内置能力与外部插件 |
| `Tool::call` | `Tool::call` 是同步签名、`Host::call_tool` 是异步，这里与 MCP 桥同口径：搬进独立线程 + 独立 current_thread 运行时。**不用 `Handle::block_on`**——调用方就在 tokio worker 上，那会把调度器一起堵死。线程 panic / 运行时装不起来一律折成可回灌的 `ToolFailed` |
| `call_error` | 宿主失败一律可回灌（不产 `fatal`）：插件崩了不该终止整次运行，模型可以换工具、换参数或如实告知用户「这个插件没了」。不把「路径越界」留给这里，因为插件工具的路径由插件自己管，内核没有路径可判 |
| `result_text` | 字符串原样、`null` 空串、其余序列化 JSON。不加「插件返回：」之类前缀——回灌越接近插件原意越好，前缀会被模型当数据引用 |
| `read_tool_names()` | **只挑 `risk=Read`** 的全名给闸门做直通集合；漏一个 `write` 进去就是一条绕过审批的写盘口子 |
| `inject()` | 在既有注册表上追加；`host = None` 原样返回，不给精简构建 / 单测凭空造空壳工具 |
| 单测 5 条 | 声明前缀、缺说明兜底、无宿主空操作、装载后注入 / 卸载后消失、调用往返（含卸载后回灌错误）；其中 2 条真起 node 插件子进程 |

### 1.3 内核侧：接线与闸门

| 位置 | 内容 |
|---|---|
| `crates/core/src/agent_api.rs` | `RunCtx` 新增 `plugins: Arc<Host>`，与 `mcp` **同口径现取**：注册表在每次运行开头重建，运行前刚装载的插件立即可用；中途卸载 / 崩溃只会在调用时报错，不会把已建好的注册表变成幽灵工具。`run_loop` 里 `mcp_tools::inject` 之后再 `plugin_tools::inject`，闸门构造后 `.with_extra_read_tools(read_tool_names(&ctx.plugins))` |
| `crates/core/src/state.rs` | `plugins: Host` → `Arc<Host>`（`plugins()` 返回 `&Arc<Host>`）：agent 侧要跨线程持有，且 `Host` 内部本就是 `Mutex<HashMap>`，包一层 `Arc` 不影响单测里「不装就能直接装载」的性质 |
| `crates/core/src/lib.rs` | 导出 `plugin_tools` 模块，注明「P3：把 `plugin__<id>__<tool>` 挂到 agent 注册表」 |
| `crates/agent/src/permission.rs` | `PermissionGate` 新增 `extra_read: Mutex<HashSet<String>>` 与 `with_extra_read_tools` / `extra_read_tools` / `is_extra_read`。`ruling()` 的只读分支由 `READ_TOOLS.contains(&tool)` 扩为 `READ_TOOLS.contains(&tool) \|\| self.is_extra_read(tool)`，仍走 `ruling_for_path(ctx, call, false)`——**只读直通不等于免路径校验**，越界路径照旧 `1002`，敏感路径照旧 `1003` |
| 同上：单测 2 条 | ① 登记过的只读插件工具工作区内放行 / 无路径按根放行 / 未登记的写工具仍 `Ask` / 越界路径仍 `PATH_OUT_OF_WORKSPACE`；② 不登记时一律 `Ask`（opt-in per run，绝不默认放行） |

> 为什么不把插件工具塞进 `READ_TOOLS` / `WRITE_TOOLS`：那两张是编译期常量表，而插件工具随装载状态每次运行都不同。运行期集合与编译期常量分开，才不会出现「P3 之后内置工具口径被顺手改掉」这种连带风险。

### 1.4 端到端：`crates/core/tests/plugin_tool_flow.rs`（新增）

不经过内核进程，把「真插件子进程 + `plugin_tools::inject` + `PermissionGate` + 脚本化模型」拼成完整闭环：装载表 → 注册表 → 闸门 → 插件回包，链条上任何一环脱节都跑不通。插件替身是 node 脚本：`peek` 声明 `risk=read`、`poke` 声明 `risk=write`，**被调用才落 `poked.txt` 标记文件**——标记文件在不在就等于「插件到底有没有被执行过」。

| 用例 | 钉住什么 |
|---|---|
| `read_tool_runs_quietly_and_denied_write_never_reaches_the_plugin` | 只读工具一次审批都不弹（`StubDecider` 的待办队列恒为空），回包真的回到模型面前；写工具触发审批、被拒后回灌一条工具错误、循环继续到 `Completed`；`poked.txt` **不存在** → 「拒绝后无副作用」 |
| `approved_write_tool_executes_inside_the_plugin` | 审批通过后写工具真的执行到插件内部（`poked.txt` 存在且内容对得上），工具结果回到模型 |

## 二、验收判定对照

| docs/14 §13 P3 判定 | 证据 | 结论 |
|---|---|---|
| 模型可调用插件工具 | 注册表内名为 `plugin__demo__peek` / `plugin__demo__poke`；两个 e2e 用例均由脚本化模型发起调用，结果以 `role=tool` 消息回灌（`results[0]` 内含 `"tool":"peek"` 与插件原样回包）；`plugin_tools` 单测覆盖「装载后注入 / 卸载后消失」 | 达成 |
| `risk=write` 触发审批 | 同一轮里 `peek` 走 `Ruling::Allow` 不问，`poke` 走 `Ruling::Ask` 问；`permission` 单测另钉「未登记的写工具仍 Ask」「不登记时连只读也 Ask」 | 达成 |
| 拒绝后无副作用 | 拒绝路径下插件进程一次都没被调用（`poked.txt` 不存在），且拒绝只回一条工具错误、`stop_reason = Completed`、`assistant_errors` 恰好 1 条 | 达成 |

补充口径一处：**审批被拒的调用不计入 `steps`**。这是 runner 既有口径（`state.steps += 1` 在闸门之后），P3 沿用并在用例里显式断言「只有只读那一步真的执行了」。两条调用各有一条配对结果，审计侧不会出现孤儿 `tool_call`。

## 四、已知限制

1. **`plugin.call` 仍是 `6101` 空分支**。P3 走的是 agent 注册表注入，外壳侧不需要、也没有放行 `plugin.call`。该网关与 `grant` / `revoke` 一并留给 P4。
2. **审计未接**。本切片之后插件的写操作已经真的会发生，但 `audit.list` 里还没有插件调用行——docs/14 §13 的「P3 与 P4 必须同版本发布」仍然有效，P4 未落地前**不可对外发布**。
3. **只读直通是「声明信任」**。`risk` 取自插件握手自报的声明，内核无法核对插件实际行为：一个声明 `risk=read` 却偷偷写盘的插件能拿到免问通道。这与 docs/14 §8 的威胁模型一致（插件在安装时等于运行任意代码），但 UI 文案不能说「只读插件绝对不写盘」。
4. **鉴权粒度只到工具级**，没有按参数细分。同一插件内 `read` 与 `write` 工具各自定级，但无法表达「这个工具只在 `src/` 下算只读」。
5. **调用超时 30 s 固定**，未接清单里的 `timeoutMs` 与宿主配额（§8.4 的调用次数上限仍是 P4 的事）。
6. **同一次运行内装载状态是快照**。运行中途装载的插件要等下一次运行才进注册表（与 MCP 连接同口径），这是刻意的：不给运行中的注册表做热插拔，避免模型看到一半变化的工具表。
7. **`plugin__` 前缀未做长度/字符白名单**。命名空间名由宿主按 `<id>__<tool>` 拼，`id` 与工具名的合法性目前由清单校验保证（P1），没有针对「拼出超长名字顶爆注册表展示」的额外限制。
