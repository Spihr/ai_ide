## 三、逐条验收

### 3.1 撤销能力后调用返回 `6103`

| 项 | 内容 |
|---|---|
| 实现 | `revoke` 撤授权位后按账本重算剩余集，当场 `FsHostApi::set_granted_for`；闸门①在 `FsHostApi::call` 的最前面，未授权直接 `unauthorized` → `6103` |
| 证据 | `plugin_api::tests::revoke_takes_effect_on_next_host_call_without_reload`：撤 `fs.read` 后下一次 `host/fs.read` 返回 `PLUGIN_CAPABILITY_DENIED`；`revoke_key_capability_flips_ready_plugin_back_to_needs_grant`：撤 `fs.write` 后剩余集只剩 `fs.read` |
| 关键设计 | **不 reload**。撤销是「运行态止损」而不是「下次装载才生效」——否则插件在撤销到重载之间仍能读一整段时间，撤销就成了记账动作 |
| 结论 | **达成** |

### 3.2 审计行数与宿主调用数一致

| 项 | 内容 |
|---|---|
| 实现 | 四类插件事件统一成一套行形状（`BASE_FIELDS = pluginId / action / target / decision / callId`）：`plugin.host_call`（P3.5）、`plugin.capability_changed`、`plugin.call`、`plugin.lifecycle`（`711afeb`） |
| 一致性规则 | 每次 `host/*` 必落一行，**含 `deny` / `quota_exceeded`**；`plugin.call` 的四种拒绝（畸形 / `6101` / `6102` / `6106`）各落一行 `deny`；`grant` 的成功与被拒各一行；`unload` 一行 |
| 唯一例外 | 方法名本身不存在（`capability_of` 返回 `None`）不落行——连能力都谈不上，记了只会污染「插件用过什么」 |
| 证据 | `grant_records_allow_and_deny_rows`（`rows.len() == 2`，一次请求一行不许多也不许少）；`call_gateway_records_deny_rows_with_call_id`（3 次拒绝 → 3 行，`callId` 与请求 id 一致）；`unload_records_lifecycle_rows`（1 次卸载 → 1 行，`actor = user`）；`revoke_records_capability_row_with_unloaded_flag`（`rows.len() == 1`）；`successful_call_is_audited_with_all_fields`（1 次成功 `host/*` → 1 行字段齐全）；`quota_is_enforced_and_audited`（第 201 次超配额留 `quota_exceeded` 行）；`plugin_tool_flow.rs` 端到端 `assert_eq!(rows.len(), 1)` |
| 口径偏差 | 未做「连发 N 次后总行数 == N+1」的整数断言，改用 `wait_audit` 轮询 + 单点计数。原因是审计只在有 Tokio 运行时才 `spawn` 落库（同步单测里直接跳过，绝不 `block_on` 卡帧泵），总数断言会与异步落库竞态；用「存在性 + 每次调用恰好一行」的用例组合等价覆盖 |
| 结论 | **达成**（口径已写明） |

### 3.3 写侧拒绝后不产生文件

| 项 | 内容 |
|---|---|
| 实现 | 闸门③审批排在「参数解码 → 目标形状」之后、配额之前：`Reject` 或**无人安装审批器**（fail closed）一律 `TOOL_NOT_ALLOWED`，且不进入 `fs_write` |
| 证据 | `fs_write_rejection_leaves_no_file`：拒绝后 `note.txt` 不存在、`temp_files(&root)` 为空（临时文件也不许留）、审批只问一次、`quota_used == 0`（**审批排在配额前面**，被驳回的写不消耗额度）；`fs_write_without_approver_is_rejected`：没装裁决方 = 无人能批准 = 拒，文件同样不落盘 |
| 结论 | **达成** |

### 3.4 原子写

| 项 | 内容 |
|---|---|
| 实现 | 目标**同目录**建 `WRITE_TEMP_PREFIX-<seq>.tmp` → 写入 → `sync_all()` → `rename`；父目录不存在先 `create_dir_all`（v1 无 `fs.mkdir`，不补建插件连第一个文件都写不了） |
| 证据 | `fs_write_replaces_atomically_without_temp_leftovers`：覆盖已有文件后内容为新值、目录内无 `.aiide-write*` 残留；失败分支同样清理临时文件 |
| 限制 | `rename` 只在同卷原子——写侧的临时文件落在目标同目录，同一工作区内恒成立；跨卷（挂载点/网络盘）不在保证内。`fsync` 先于 `rename`，避免「名字对、内容空」的半文件 |
| 结论 | **达成**（同卷语义，已在代码注释写明） |

### 3.5 授权即时生效

| 项 | 内容 |
|---|---|
| 实现 | `grant` 逐项写授权位 → 按账本**重算**（不做差分，防漏算一项等于白授权）→ `set_granted_for` |
| 证据 | `grant_writes_ledger_and_runtime_grants_without_reload`：授权前撞 `6103`；授权后账本与返回值一致、状态回 `Disabled`；再调 `host/fs.read` 撞的是 `1001`（工作区未开）而**不是** `6103`——说明授权已进运行态，无需 reload |
| 结论 | **达成** |

### 3.6 关键能力撤销连带 `unload`

| 项 | 内容 |
|---|---|
| 判据 | `KEY_CAPABILITIES = ["fs.write", "net.fetch", "llm.chat"]`：写 / 网络 / 外部模型是「清单里 `risk=write` 工具承诺的前提」，缺了它插件起来也只会一路 `6103`，把模型拖进「调用→被拒→重试」循环，所以整个插件下架；读类撤销只是收窄可读面，插件照常跑 |
| 实现 | `revoke_capabilities`：`was_running = is_running(plugin_id)`，`unloaded = critical && was_running`；真卸时先 `unload`（工具下架）再清空授权集；账本一律退回 `needs_grant`，`crashed` 保留原样（崩溃原因比这次撤销更值得留在面板上）；`unloaded` 落进审计 `note` |
| 证据 | `key_capabilities_cover_write_network_and_llm_only`（恰好那三个，读类不在其中）；`revoke_key_capability_flips_ready_plugin_back_to_needs_grant`（关键能力撤销 → `needs_grant`，工具不再被路由）；`revoke_records_capability_row_with_unloaded_flag`（`unloaded` 字段落审计） |
| 口径偏差 | 上述用例断言的都是 `unloaded == false`（测试环境没起真子进程）；`was_running == true` → 真卸这一支依赖 P2 已验收的 `Host::unload`（工具下架 + 进程回收），P4 未再起真子进程复测。这是**分支复用**而非未覆盖 |
| 结论 | **达成**（真卸支路待真机清单补一条） |

### 3.7 `plugin.call` 六步定序

| 项 | 内容 |
|---|---|
| 六步 | ① 参数快照校验（空 `plugin_id` / `method` → `-32602`）→ ② 账本无记录 → `6101` → ③ 非 `ready` 或进程不在 → `6102` → ④ 未声明该方法 → `6106` → ⑤ 转发 `plugin/tool-invoke`（`params` 缺省 `{}`）→ ⑥ 64 KB 截断后回灌 |
| 为何不可交换 | ①→②：畸形请求不能借 `6101` 回答「你参数写错了」；②→③：没这插件与有但跑不起来要分开报（前者让模型别再编名字，后者让用户去面板看它为什么挂）；③→④：**`6106` 早于能力判定**——归属校验只看插件自己声明的清单，反过来先判能力会让越权请求拿到「你没授权」，把方向指到授权上 |
| 证据 | `gate_reports_the_first_failing_step_only`（六步逐级只报第一个失败步）；`attribution_error_precedes_any_capability_verdict`（`6106` 且断言 `!= 6103`）；`snapshot_distinguishes_installed_from_running`（装了没跑是 `6102` 不是 `6101`）；`relay_failures_map_to_their_own_codes`（超时 `6105` / 越权工具 `6106` / 插件自报错误原样带码）；`content_over_limit_is_truncated_on_char_boundary`（64 KB 硬上限、截断点回退到字符边界，绝不产出非法 UTF-8）；`call_gateway_records_deny_rows_with_call_id`（三种拒绝各留一行，`callId = 请求 id`） |
| 结论 | **达成** |

## 五、未达成项与已知限制

### 5.1 【阻塞】授权面板被 IPC 白名单挡住

**事实链**：

1. `PluginPanel` 的「授权 / 全部授权 / 撤销」→ `plugin-store` → `plugin-api.ts` 的 `window.aiide.request(Methods.plugin.grant | revoke)`；
2. `apps/desktop/src/main/index.ts:329` 对每条渲染进程请求先过 `checkRendererCall(method)`；
3. `apps/desktop/src/main/policy.ts` 的 `allowedRendererMethods` 仍只有 7 项插件方法：`plugin.install` / `list` / `status` / `uninstall` / `load` / `unload` / `reload`，**`grant` / `revoke` / `call` 不在其中**；
4. `policy.test.ts:161` 甚至有一条用例显式断言这三者「不应被放行」（写于 P1/P2 时期，当时内核还是 `6101`）。

**后果**：用户点授权/撤销，拿到的是「渲染进程无权调用 plugin.grant；如需开放，请在 main/policy.ts 中显式加入白名单」，而非 `plugin.grant` 的结果。P4 的「授权面闭环」目前只在**内核层**成立，UI 层是死链。审计视图与写侧审批不受影响（走 `audit.list` / `agent.decide`，均在白名单内）。

**修复方案**（未在本提交内实施——放行白名单属安全边界变更，需用户确认后单独提交）：

| 改动 | 内容 |
|---|---|
| `policy.ts` | 白名单补 `Methods.plugin.grant` / `revoke` / `call` |
| `policy.test.ts` | 把「不放行 P3/P4 方法」的断言反转成「放行并给出风险说明」：`grant` / `revoke` 一次只能改本机已装插件的授权位（内核核清单）、`call` 只能调已装载插件声明过的方法（内核六步校验），二者都不含路径/命令参数 |

不顺手改的理由：白名单是该项目的安全基线（`policy.ts` 注释明确「放行前先想清楚 UI 有没有二次确认」），`call` 还会把「模型调插件」变成「渲染进程可直接调插件」，需要单独一次变更 + 回归，不能混进验收报告提交。

### 5.2 其它已登记边界

| 项 | 说明 |
|---|---|
| `net.fetch` / `llm.chat` / `host/progress` | v1 无实现，仍 `-32601`；因此「撤 `net.fetch` 连带卸载」只能按 `KEY_CAPABILITIES` 名单判定，没有可执行路径验证 |
| 写侧审批离线/无 UI | 无审批器、无活动工作区、无 Tokio 运行时三种情况一律 `Reject`（fail closed），不存在「悄悄放行」分支 |
| 审计不可被插件篡改 | `HostApi` 只有六个 `host/*` 方法，`host/audit.list` 当场 `-32601`；仓储层 `audit` 表只有 `INSERT` / `SELECT`。`plugins_cannot_reach_or_rewrite_audit` 用例钉住 |
| 审批记忆粒度 | `allow_always` 按「文件绝对路径」落一条免问规则（`WRITE_TOOL = "fs.write"`），不是按目录——同目录新文件仍会再问一次 |
| 提交序列 | `4959eb8` 的 `typecheck` 断言早于最后一次 JSX 改动落盘，`e80f5f4` 才恢复绿灯。教训：前端提交应「改完再跑一次门禁」，不能拿改动前的绿灯当结论 |

## 六、结论

1. **P4 内核验收：通过**。八项判定逐条有实现、有用例、有证据；四项口径偏差（审计计数用轮询替代总数断言、关键能力真卸支路复用 P2、原子写限同卷、`net.fetch` 无实现）均已在正文写明，不构成掩盖。
2. **P4 前端验收：部分通过**。审计视图与写侧审批 UI 达成；授权面板界面完整但**请求被 IPC 白名单拒绝**，属必须修的阻塞项（一行白名单 + 一条断言反转）。
3. **对全局目标的意义**：插件从「能装、能跑、能读」推进到「能写但必先获批、调用可追溯、权限可收可放」——P4 之后插件系统的信任模型已闭合到「内核裁决 + 用户裁决 + 事后可查」三层，剩下的 `net.fetch` / `llm.chat` 属 P5 生态扩展的内容面，不是权限面。
4. **下一步**：① 补 `policy.ts` 白名单与 `policy.test.ts` 断言（阻塞项，建议独立提交）；② 真机清单补一条「撤关键能力时插件确在运行 → 工具下架」的实测；③ `docs/05` 里程碑表 P4 与 `docs/14` §13 落地进度已同步更新。
