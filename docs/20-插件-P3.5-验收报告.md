# 插件 P3.5 验收报告：读侧宿主能力（`host/*` 反向请求）

> 日期：2026-10-24
> 范围：`crates/plugin/src/host_api.rs`（新增，`HostApi` 契约与 `HostApiError` 九码）、`crates/plugin/src/loader.rs`（`answer_plugin_request` 纯函数、`SpawnOptions.host`、`PluginProcess::host`）、`crates/plugin/src/host.rs`（`Host::set_api` / `Resume.host` / `call_tool` 处调 `begin_call`）、`crates/core/src/plugin_host.rs`（新增，`FsHostApi` 与五个读侧方法）、`crates/core/src/state.rs`（`plugin_host` 字段与 `install_store` 回填）、`crates/core/src/ws.rs`（工作区开关跟随）、`crates/core/src/plugin_api.rs`（装载刷新授权、卸载作废）、`crates/store/src/model.rs`（`audit_kind::PLUGIN_HOST_CALL` / `audit_actor::PLUGIN`）、端到端用例 `crates/core/tests/plugin_tool_flow.rs::plugin_tool_reads_workspace_through_host_capability`，提交 `b4cc718`
> 结论：P2 起一律回 `-32601` 的插件反向请求**已真正打通**。插件工具内部发 `host/fs.read` 能读到真实工作区文件并把正文带回模型；**闸门顺序固定为能力 → 路径 → 配额**（未授权插件先撞配额会给出误导性提示，故顺序不可换）；每次调用（含被拒与超限）落一行 `plugin.host_call` 审计。写侧（`host/fs.write`）与网络 / LLM 能力**未开**，留 P4；`plugin.grant` / `revoke` 仍是 `6101`，能力清单仍是 **71 项**（P3.5 不新增协议方法）。

## 一、交付物

### 1.1 契约层：`crates/plugin/src/host_api.rs`（新增）

| 项 | 内容 |
|---|---|
| `HostApi` trait | 单方法 `call(plugin_id, method, params) -> Result<Value, HostApiError>`，**同步**。理由写在文件头：读文件、列目录都不长，实现方若在帧泵里等异步，一条慢请求会堵死该插件的所有回包 |
| `HostApi::begin_call` | 默认空实现，配额实现方才有意义。挂在**工具调用边界**（`Host::call_tool` 里 `api.begin_call(plugin_id)`），不是每次 `host/*` |
| `HostApiError` 九码 | `6103` 能力未授予、`1002` 越出工作区、`1003` 敏感路径、`1001` 工作区未打开、`1004` 不存在、`1005` IO、`6109` 配额、`-32602` 参数畸形、`-32601` 方法不存在 |
| `SharedHostApi` | `Arc<dyn HostApi>` 别名 |

分 crate 是刻意的：`crates/plugin` 只负责「把插件请求转给实现、把结果/错误封回帧」，不认识账本也不认识工作区，因此它的单测塞一个 `FakeHost` 就够，不必搭真工作区。

### 1.2 转发层：`crates/plugin/src/loader.rs`

- **`answer_plugin_request(host, plugin_id, id, method, params) -> Value`**：纯函数，不碰 IO、不碰装载表，可单测。三道判定按序：
  1. **命名空间**：只有 `host/*` 可由插件发起；`plugin/*` 等反向调用属越权（docs/14 §8.2 T4），回 `-32601`；
  2. **接线**：宿主没装实现时如实回 `-32601`（消息含「宿主能力尚未接线」），**绝不假装成功**——假数据会让插件带着错误假设继续跑；
  3. **转发**：错误码原样透传，闸门怎么判由实现方决定。
- `dispatch_frame` 的 `(id, method)` 分支由「统一回 -32601」改为「解析 `params`（非对象一律当 `{}`）→ `answer_plugin_request` → 写回帧」，写失败的消息从「回绝」改成「回复」。
- `SpawnOptions.host` / `PluginProcess::host()`：出口随进程对象走，`pump_stdout` 拿得到。

### 1.3 装载层：`crates/plugin/src/host.rs`

- `Host::set_api(Arc<dyn HostApi>)` / `Host::api()`：`Option<Arc<dyn HostApi>>` 存在 `Mutex` 里，只为让 `Host` 保持 `Sync`（`Arc<Host>` 被 `AppState` 跨线程持有），实际只在装配时写一次。
- `Resume.host`：自动重启沿用它——否则一次崩溃重启后 `host/*` 会突然退回 `-32601`，插件在同一次工具调用里前后拿到两种答案。`Resume` 因此**不再派生 `Debug`**（`dyn HostApi` 钉不出有意义的调试串）。
- `call_tool` 在 `plugin/tool-invoke` 前调 `begin_call`：配额口径是「单次工具调用 ≤ 200 次」，归零点必须在工具调用边界。

### 1.4 实现层：`crates/core/src/plugin_host.rs`（新增，966 行）

| 项 | 内容 |
|---|---|
| `FsHostApi` 字段 | `root`（活动工作区根，`RwLock<Option<PathBuf>>`）、`granted`（缺省集）、`by_plugin`（按插件分账的授权集）、`store`（`RwLock<Option<Store>>`，晚装可生效）、`quota`（`Mutex<HashMap<String, usize>>`）、`calls`（`AtomicU64`，拼 `callId`） |
| 已实现方法 | `host/fs.read`（默认 64 KB 上限，超限截断并带 `truncated`）、`host/fs.list`（**单层**，不递归）、`host/fs.stat`、`host/search.content`（跳过 `node_modules` / `target` / `.git` / `.hg` / `.svn`，单文件 1 MiB 上限，默认 50 条，超量置 `truncated`）、`host/workspace.info` |
| 未实现方法 | `host/fs.write`、`host/net.fetch`、`host/llm.chat`、`host/progress` → `-32601`，**且不落审计**（连方法都不存在，谈不上「用了什么能力」） |
| 路径闸门 | 形状（禁绝对 / 禁 `..` / 禁盘符与 UNC / 禁 NUL）→ 敏感段（`.git` `.ssh` `.aws` `.kube` `.env`）→ 规范化后**复核**前缀与敏感段 |
| 审计 | `plugin.host_call`，`actor=plugin`，`session_id` 留空，`detail` 含 `pluginId` / `method` / `capability` / `target` / `decision`（`allow` / `deny` / `quota_exceeded` / `error`）/ `callId`（`host-N`）；**异步 `spawn` 落库**，拿不到 Tokio 运行时（同步单测）就跳过——这条路径上绝不能 `block_on`，那会把帧泵连同回包一起卡死 |

路径闸门的「规范化后复核」不能省：`link/.ssh` 这种「先符号链接再进敏感目录」的写法，只有 `canonicalize()` 之后才看得见；单测 `path_gate_rejects_absolute_parent_and_sensitive` 覆盖四条拒绝路径。

### 1.5 内核接线

| 位置 | 改动 |
|---|---|
| `AppState::new` | 先建 `FsHostApi`、再 `plugins.set_api(...)`。顺序不能反——插件反向请求没有「稍后重试」这一说，没挂上就只能回 `-32601`，而那时插件已经起来了 |
| `AppState::install_store` | 回头补 `plugin_host.set_store(store.clone())`。宿主能力在 `new` 就活了，库是启动后才连上的，不补这一步 P3.5 之前的 `host/*` 调用会静默丢审计 |
| `ws::open` | `set_root(Some(root))`：相对路径都相对活动工作区解析，多工作区下后开的那个成为默认靶子，与 `workspace.tree` 的既有口径一致 |
| `ws::close` | 关掉活动区后**重算**根：有别的区还开着就换过去，没有就彻底关闸（回 `1001`）。不保留旧根——「已关闭的工作区仍然可读」是最难解释的一种泄漏 |
| `plugin_api::load_into` | `set_granted_for(plugin_id, granted)`：`host/*` 的能力闸门要**当场**知道账本结果，不能每次调用回库查 |
| `plugin_api::unload` | `set_granted_for(plugin_id, vec![])`：进程已没了，留着这份授权只会让下一次同名重装继承上一轮的权限 |

## 二、判据与证据

| 判据 | 证据 |
|---|---|
| 插件工具内部能反向读宿主工作区 | `plugin_tool_flow.rs::plugin_tool_reads_workspace_through_host_capability`：fixture 插件的 `probe` 工具在内部 `await askHost('host/fs.read', ...)`（真走 stdin/stdout 帧协议，不是桩），断言工具结果里出现磁盘正文 `HOST-READ-OK`、无 `<tool_error`、`model.calls()==2` |
| 闸门顺序：能力先于配额 | `plugin_host::tests::unauthorized_plugin_is_rejected_before_quota`：未授权插件拿到 `6103` 而不是 `6109` |
| 路径闸门 | `path_gate_rejects_absolute_parent_and_sensitive`：绝对路径 / `..` / `.git` / `.env` 四条全拒 |
| 读语义 | `fs_read_marks_truncation`（超 64 KB 截断并标记）、`fs_list_is_single_level`（子目录不展开）、`search_content_hits_and_skips_node_modules` |
| 配额与审计 | `quota_is_enforced_and_audited`：第 201 次 `6109`，审计里有 `quota_exceeded` 行；`begin_call` 后计数归零 |
| 审计字段 | `successful_call_is_audited_with_all_fields`：`actor=plugin`、`kind=plugin.host_call`、`pluginId/method/capability/target/decision` 齐全、`callId` 以 `host-` 开头、`session_id` 为空 |
| 未接线不假装成功 | `loader::tests::host_request_without_api_is_method_not_found`、`non_host_namespace_is_rejected`、`api_error_passes_through_code_and_message`、`host_request_is_forwarded_to_api` |
| 未实现方法 | `unimplemented_method_answers_method_not_found` |
| 端到端审计 | 同一 e2e 用例断言审计恰好 1 行且方法为 `host/fs.read`、`decision=allow` |

门禁：`cargo fmt --all -- --check` 通过；`cargo clippy --workspace --all-targets -- -D warnings` **0 error**；`cargo test --workspace` **1022 passed / 0 failed**（44 个测试二进制，含上述 e2e）。

测试写法的两个坑（已在本轮修掉，留给后续参考）：

1. **审计是异步 `spawn` 的，不能用固定 `sleep` 赌时序，也不能「等第一行就返回」**。`wait_audit` 初版只等「有行」，`quota_is_enforced_and_audited` 拿到的是前 50 行（默认 `limit=50`）就提前返回，断言 `quota_exceeded` 假失败。现改为「等出现满足条件的行」+ `with_limit(500)`。
2. **clippy 的 `unused variable` 会杀掉门禁**，而「先写 `let (api, store)` 再补断言」正是最容易漏的地方——测试里用不到 `store` 就应该直接不接。

## 三、已知限制

1. **写侧未开**：`host/fs.write` 回 `-32601`。docs/14 §7.1 要求它「双闸门 + 临时文件 rename」，依赖逐次审批，属 P4 与 `grant` / `revoke` 同批落地。P3 之后工具已能被模型调用，P3.5 又开了读，写侧再拖下去不会有安全空窗（写操作现在根本发不出去），但插件能做的事就停在「只读」。
2. **授权集是装载时快照**：`FsHostApi` 里的授权只在 `load_into` / `unload` 刷新。P4 接 `plugin.grant` / `revoke` 时**必须**在同一处回写，否则会出现「账本已授权、运行中的插件仍被 `6103` 挡」或反向的「已撤销但仍可读」。
3. **`host/progress` 未实现**：长任务进度（docs/14 §7.3）仍缺，30 s 超时是硬墙不变。
4. **配额粒度是进程内计数**：计数随 `begin_call` 归零，不做跨工具调用的滑动窗口；单次调用 200 次的上限对读侧足够，写侧落地时需重新评估（一次批量写很容易撞 200）。
5. **`search.content` 是线性遍历**：只跳固定目录、不建索引、单文件 1 MiB 上限；大仓首次搜索会慢，接 `crates/indexer` 留给后续切片。
6. **未做真机人工验收**：本轮全部证据来自自动化用例，插件在真界面里读工作区的体感未实测。

## 四、与 docs/14 的口径差异

| 文档原文 | 实现口径 | 原因 |
|---|---|---|
| §7.1 `workspace.info`「跟随 `fs.read`」 | 独立能力串 `workspace.info`，但 `is_granted` 对含 `fs.read` 的授权集返回真 | 保留能力名给未来细分留口子，同时不逼插件在清单里多写一项 |
| §7.2 `host/fs.write` 在 P3.5 范围内 | 回 `-32601` | 写侧依赖审批映射与审计闭环，与 P4 同批才有意义 |
| §8.3 审计「一次宿主调用一行」 | 一次宿主调用一行，**含被拒与超限**；未实现方法**不落行** | 「这个插件试过什么」比「它成功读了什么」更接近审计的目的；方法不存在连能力都谈不上 |
| §3 能力清单 71 项 | 仍是 71 | P3.5 只填 P2 时期就登记在册的 `host/*` 空分支，不新增协议方法 |
