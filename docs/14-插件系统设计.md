# 12 · 插件系统设计

> 状态：**设计定稿，未接线**（P0 未开工；`crates/plugin-host` 尚未进 workspace）
> 关联：[02 §8 安全模型](./02-系统架构设计.md) · [03 内核接口协议规范](./03-内核接口协议规范.md) · [04 AI 能力与 Agent 设计](./04-AI能力与Agent设计.md)
> 可运行验证：`demo-plugin-system/`（`node run-demo.mjs`，12/12 通过）

## 1. 定位

插件系统要解决的是：**在不改动内核的前提下，让第三方代码提供 Agent 可调用的能力和用户可触发的命令**。

"不改动内核"是硬约束。一旦允许插件注册方法名、挂钩子、替换工具实现，`dispatch.rs` 的穷举 match 立刻失效，`core.hello` 的能力清单也会开始撒谎。所以本设计的全部难点不在于"怎么把插件跑起来"，而在于**怎么让插件跑起来的同时，内核仍然是一份静态可审计的方法表**。

答案是把插件的能力**收敛到一个入口**：`plugin.call`。所有插件方法都在这个网关背后，方法名不出现在 `methods::IMPLEMENTED` 里。

### 1.1 范围

| v1 做 | v1 不做（协议位预留或明确不排期） |
|---|---|
| 插件包规范与清单校验 | UI 贡献点（面板、状态栏、主题、语法高亮） |
| 安装 / 卸载 / 加载 / 卸载运行 / 重载 / 授权 / 撤销 | 插件市场、签名、自动更新 |
| Agent 工具扩展（注入 ToolRegistry） | 插件间直接通信 |
| 用户命令扩展 | 内嵌多语言运行时（只 spawn 可执行文件） |
| 单向事件订阅（宿主 → 插件） | 拦截/改写内核行为（无钩子、无中间件） |
| 宿主 API：文件、搜索、工作区信息、长任务进度、日志 | LLM 直调（`host/llm.chat` 只有闸门，无实现） |
| 四道闸门 + 审计 + 资源配额 | 权限的按次临时放行（v1 只有 always / 拒绝） |

### 1.2 一句话结论

> 插件是**独立子进程**，用 **NDJSON over stdio** 跟 **Core 侧的 plugin-host** 说话；它拿不到文件系统，只能请求 `host.*` 能力，每次请求都要过 **能力闸门 → 路径闸门 → 审批闸门 → 配额**；它的工具以 `plugin.<id>.<name>` 注入 `ToolRegistry`；它的方法名**永不**进内核方法表。

## 2. 继承的约束

以下四条是现有实现的不变量，不是建议。插件设计必须逐条对上。

| 不变量 | 现状依据 | 对插件系统的直接约束 |
|---|---|---|
| `core.hello` 上报的能力清单必须真实 | `dispatch.rs` 是穷举 match，`methods::IMPLEMENTED` 与分支一一对应 | 插件方法不进 `IMPLEMENTED`；只加 10 个 `plugin.*` 固定方法 |
| stdout 专用于协议帧 | Core 与 Main 之间是 stdio NDJSON | 插件 stdout 只写帧；日志必须走 stderr，否则判 6106 |
| 副作用集中在 Core | 02 §8：路径规范化、命令黑名单、敏感路径拒写全在 Core | 宿主必须在 Core，插件不能自己碰磁盘 |
| 模型输出不可信 | 02 §8 要点 2 | 插件返回的内容同样不可信：只当 tool result 文本回灌，不解析为控制流 |

第 4 条容易被忽略。插件工具的输出会直接进模型上下文，而插件是第三方写的——**它的返回值和模型输出一样不可信**。这一点决定了 §8.5 的两条规则。

## 3. 决策记录

接续 02 的 ADR-1 ~ ADR-7。

| # | 决策 | 备选 | 理由 |
|---|---|---|---|
| ADR-8 | 插件是**独立子进程**，与宿主用 stdio NDJSON 通信 | ①同进程动态库 ②WASM 沙箱 ③本地 HTTP | ①崩溃带崩 Core、ABI 地狱、无法限流；②生态与调试能力差，Node/Python 插件写不了，且文件能力仍需自己实现；③端口与防火墙问题（与 ADR-2 同因）。子进程换来崩溃隔离、语言无关、可用 OS 级资源限制，代价是一次 IPC 往返（毫秒级） |
| ADR-9 | 宿主落 **Core**，不落 Main | 放 Main（Node 侧） | 02 §8：能力实现点全在 Core。放 Main 等于让插件绕过 PathGuard / PermissionGate / 审计三件套，或者在 Main 重写一遍 |
| ADR-10 | 插件方法走 **`plugin.call` 网关**，不动态注册 | 运行时往方法表注入 | 会破坏 ADR-1 以来的"能力不虚报"不变量；穷举 match 变成动态派发后，协议层再无法静态审计 |
| ADR-11 | v1 扩展点只做 **工具 + 命令** | 同时做 UI 贡献点 | UI 贡献点要打通 Core→Main→Renderer 三段事件链，且 Renderer 是 sandbox 的，插件 UI 一旦能执行就是新的攻击面。先把能力面做扎实 |
| ADR-12 | 能力**两层**：安装期 `capabilities`（粗）+ 调用期审批（细） | 只做其中一层 | 只有安装期授权：插件拿到 `fs.write` 就能静默改任意工作区文件；只有调用期：插件每次启动都要用户点十几次。两层叠加后，"装的时候知道它想要什么，用的时候确认它现在做什么" |
| ADR-13 | `pluginApi` **major 严格匹配**，minor 向下兼容 | 全部严格 / 全部宽松 | major 变更意味着帧结构或闸门语义变了，不能猜；minor 只加字段/加方法，旧插件不受影响 |

ADR-8 的代价要说清楚：**子进程意味着跨进程序列化开销**。一次 `repo_stats` 在 demo 里发起了 4 次 `host/fs.list`，即 4 次往返。这是选 A 形态必须接受的成本，对策是 §7.6 的批量原语（`fs.readMany`），而不是让宿主内置递归遍历——宿主一旦内置"智能遍历"，它的规则就会和插件期望的不一致，而插件作者无法改。

## 4. 进程与生命周期

### 4.1 进程拓扑

```
┌────────────┐  白名单 IPC   ┌────────────┐   JSON-RPC    ┌──────────────────────────┐
│ Renderer   │ ────────────▶ │   Main     │ ────────────▶ │  Core                    │
│ sandbox    │               │ 策略裁决   │   stdio       │  ┌────────────────────┐  │
└────────────┘               └────────────┘               │  │ PluginHost         │  │
                                                          │  │  ├ PathGuard       │  │
                                                          │  │  ├ PermissionGate  │  │
                                                          │  │  └ 审计             │  │
                                                          │  └─────────┬──────────┘  │
                                                          └────────────┼─────────────┘
                                                                       │ stdio NDJSON
                                                          ┌────────────▼─────────────┐
                                                          │ plugin 子进程 × N        │
                                                          │ （无文件系统凭据，无网络） │
                                                          └──────────────────────────┘
```

插件是**第四类主体**，02 §8 的双闸门因此变成三主体：Renderer 不可信、插件不可信、Main 裁策略、Core 校能力。插件与 Renderer 的区别是它由用户显式安装并授权，所以它的能力可以比 Renderer 宽，但**必须逐次可见**（审计）而非静默。

### 4.2 状态机

```
                 install（仅写盘，不起进程）
                       │
                       ▼
   ┌──────────┐   grant 满足清单   ┌──────────────┐   spawn + hello   ┌───────┐
   │ disabled │ ────────────────▶ │ needs_grant  │ ─────────────────▶ │ ready │
   └──────────┘                   └──────────────┘                    └───┬───┘
        ▲                                  ▲                             │
        │ uninstall                        │ revoke 关键能力              │ 进程退出
        │                                  └─────────────────────────────┤
        │                                                                ▼
        │                            ┌───────────┐   ≤3 次自动重启   ┌─────────┐
        └────────────────────────────│  crashed  │ ───────────────▶ │ loading │
                                     └───────────┘                   └─────────┘
```

几条硬规则：

1. **`crashed` 立刻下架工具**，不等重启成功。模型看不到工具，就不会去调它；留着工具在表里但调用报错，会让模型陷入"重试—失败"循环。
2. **重启上限 3 次**，超过后停在 `crashed` 并等待用户手动 `plugin.load`。没有上限的自动重启会变成崩溃循环，把 Core 的日志刷满。
3. **`revoke` 掉关键能力后立即 `unload`**（不重启），因为它已经无法履行清单承诺。
4. **`needs_grant` 状态不 spawn 进程**。这是场景 02 断言的："返回 6103 且进程未启动"——不能让一个没被授权的插件先跑起来再拒绝它。

### 4.3 握手

```
宿主                                      插件
  │ spawn(node index.mjs)                   │
  │────────────────────────────────────────▶│
  │ {"id":"1","method":"plugin/handshake",  │
  │  "params":{host,pluginApi,capabilities, │
  │            limits}}                     │
  │                                         │ 校验：API 兼容？能力够不够？
  │◀────────────────────────────────────────│
  │ {"id":"1","result":{ok,plugin:{...},    │
  │  tools:[...],commands:[...]}}           │
  │                                         │
  │ 校验：工具集合 == 清单？名称合法？        │
  │ 不一致 → 6106，杀掉进程                  │
```

**双向校验**是关键设计。插件多报工具（清单没写、代码里实现了）等于运行时偷偷扩权；少报（清单写了、代码没实现）是清单骗人。两者都拒载，工具定义**一律以清单为准**，插件上报名单只用于比对。

握手响应里 `host` 字段可以带回插件版本与作者，用于诊断面板展示。

## 5. 包规范

### 5.1 目录

```
my-plugin/
├── plugin.json        必需：清单
├── index.mjs          必需：main 指向的入口
├── README.md          可选
└── ...                可选资源
```

`main` 必须是包内相对路径，规范化后不得越出插件目录（demo 场景 01 断言了这一条：`../../../evil.mjs` 被拒）。

### 5.2 清单字段

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | ✓ | `^[a-z0-9][a-z0-9-]{1,63}$`，全局唯一，工具名前缀来源 |
| `name` / `version` / `description` | string | ✓ | 展示用；`version` 必须 `x.y.z` |
| `pluginApi` | string | ✓ | 声明面向的宿主 API 版本，major 必须等于宿主 |
| `main` | string | ✓ | 入口相对路径 |
| `capabilities` | string[] | ✓ | 申请的能力集，见 §7.1；未知能力直接拒载 |
| `tools` | object[] | — | `{name, description, risk, parameters}` |
| `commands` | object[] | — | `{name, title, args?}`，命令面板入口 |
| `subscriptions` | string[] | — | 订阅的事件类型，未声明不投递 |
| `timeoutMs` | number | — | 单次工具调用超时，默认 30000，上限 120000 |

### 5.3 校验规则

按 **形状 → 语义 → 交叉** 三段顺序执行，一次报全所有错误（不是遇到第一个就退出）。这样插件作者一轮就能改完。

| 段 | 检查 | 失败码 |
|---|---|---|
| 形状 | 必填字段存在、类型正确、`tools[].parameters` 是合法 JSON Schema 子集 | 6107 |
| 语义 | id 格式、semver、`main` 不逃逸、能力名在白名单内、`pluginApi` 兼容 | 6107 / 6104 |
| 交叉 | `risk` 与能力一致：`write` 必须申请 `fs.write`；工具名不重复、不与核心工具冲突 | 6107 / 6108 |

"risk 与能力矛盾"这条最容易被当成吹毛求疵，但它防的是：插件声明 `risk=read`（不触发审批）却在实现里调 `host/fs.write`。能力闸门会拦住，但如果它**根本没申请** `fs.write`，那就是清单在撒谎，应该在装载前就拒掉——demo 场景 01 的最后一条错误就是这个。

### 5.4 能力变更的重授权

插件升级时若 `capabilities` 出现**新增项**，状态回退到 `needs_grant` 并重新征询。这条是防供应链攻击的主要手段：v1.0 只要了 `fs.read`，v1.1 偷偷加 `fs.write`，用户点"更新"的时候不会重读清单。

## 6. 协议

### 6.1 三类命名空间

| 前缀 | 方向 | 谁发起 | 是否进 `IMPLEMENTED` |
|---|---|---|---|
| `plugin/*` | 宿主 → 插件 | 宿主 | 否 |
| `host/*` | 插件 → 宿主 | 插件 | 否 |
| `plugin.*` | Renderer/Main → Core | 外壳 | **是**（10 个固定方法） |

前两类是**插件包内部协议**，只有宿主和插件知道；第三类是**内核协议的一部分**，要进方法表、要进 `policy.ts` 白名单、要出 TS 类型。混在一起是这类系统最常见的错误——一旦插件内部方法名出现在 `core.hello` 里，能力清单就不再是"静态可审计"的。

### 6.2 帧格式

与 Core 一致，NDJSON，一行一帧：

```json
{"id":"7","method":"host/fs.list","params":{"path":"src"}}
{"id":"7","result":{"entries":[{"name":"main.ts","dir":false}]}}
{"id":"7","error":{"code":1002,"message":"..."}}
```

约束：

- 单帧上限 **1 MiB**，超限直接终止读取并判 6106（避免一行把内存吃满）。
- 单次请求超时 **30 s**（`timeoutMs` 可覆盖，上限 120 s）。
- 通知帧无 `id`，只用于 `plugin/log`、`plugin/progress`。

### 6.3 `plugin.call` 网关

外壳侧只看到一个方法：

```json
{"method":"plugin.call","params":{"plugin_id":"demo-hello","method":"repo_stats","params":{}}}
```

宿主在这里做的事，顺序不能变：

1. 参数快照校验（`plugin_id` / `method` 必须是非空字符串，`params` 允许缺省为 `{}`）——防的是外壳被攻破后塞进来的畸形结构；
2. 查 `plugin_id` 是否存在于已加载集合，不存在 → 6101；
3. 查状态是否 `ready`，否则 → 6102（不是 6101：区分"没有这个插件"和"插件炸了"）；
4. 查方法是否属于该插件的工具/命令，否则 → 6106（插件不能调别人的方法）；
5. 转发 `plugin/tool-invoke`，等结果；
6. 结果 > 64 KB 截断并附加标记。

第 4 步容易被跳过。没有它，一个插件可以拿别人的 `plugin_id` 调别人声明的工具——虽然能力闸门还会拦（权限是绑 `plugin_id` 的），但错误信息会指错方向。

### 6.4 方法总表

| 方法 | 方向 | 说明 |
|---|---|---|
| `plugin.list` | 外壳 → Core | 列已安装插件与状态 |
| `plugin.status` | 外壳 → Core | 单个插件详情（含最近错误） |
| `plugin.install` | 外壳 → Core | 校验并写入插件目录，不启动 |
| `plugin.uninstall` | 外壳 → Core | 卸载运行 + 删目录 |
| `plugin.load` | 外壳 → Core | 授权齐备则 spawn + 握手 |
| `plugin.unload` | 外壳 → Core | 停进程 + 下架工具 |
| `plugin.reload` | 外壳 → Core | 停 + 起，用于开发调试 |
| `plugin.call` | 外壳 → Core | 网关，见 §6.3 |
| `plugin.grant` | 外壳 → Core | 授予能力 |
| `plugin.revoke` | 外壳 → Core | 撤销能力（关键能力则连带 unload） |
| `plugin/handshake` | 宿主 → 插件 | 握手 |
| `plugin/tool-invoke` | 宿主 → 插件 | 执行工具 |
| `plugin/command-invoke` | 宿主 → 插件 | 执行命令 |
| `plugin/event` | 宿主 → 插件 | 事件投递（通知帧） |
| `plugin/shutdown` | 宿主 → 插件 | 优雅退出（3 s 后强杀） |
| `host/fs.read` `host/fs.write` `host/fs.list` `host/fs.stat` | 插件 → 宿主 | 文件原语 |
| `host/search.content` | 插件 → 宿主 | 全文检索，复用内核 FTS5 |
| `host/workspace.info` | 插件 → 宿主 | 工作区根、名称、显式挂载的额外根 |
| `host/log` | 插件 → 宿主 | 日志（节流后转 `plugin.log` 事件） |
| `host/progress` | 插件 → 宿主 | 长任务进度（转 `plugin.progress` 事件） |

### 6.5 事件

宿主 → 插件单向，`subscriptions` 声明式过滤：未声明的插件**不投递**，连进程唤醒都不做。

| 事件 | 载荷 | 典型用途 |
|---|---|---|
| `workspace.changed` | `{files:[...]}` | 增量重算索引 |
| `file.saved` | `{path}` | 单文件 lint/格式化 |
| `session.started` / `session.ended` | `{sessionId}` | 会话级统计 |
| `plugin.state_changed` | `{pluginId,state}` | 插件之间无直接通信，只能靠这个感知他人状态 |

插件**不能**发事件。它只能发 `host/log` 与 `host/progress`，宿主转成带 `pluginId` 的宿主事件。这条限制挡住的是"插件伪造 `plugin.state_changed` 让宿主误以为别的插件挂了"这类攻击。

### 6.6 错误码

6xxx 段原以为是空的，**实际不是**：终端已经占了 `6001`–`6004`（会话不存在 / 启动 shell 失败 / PTY IO 失败 / 参数非法，`crates/protocol/src/error.rs` 里有一条钉死这段的断言）。

所以插件改用 **`6101`–`6109`**，段位声明为 `6101–6199`。这样两件事都不会发生：终端码被插件覆盖，或插件码踩进终端的断言。落地时 `error.rs` 里新增了 `plugin_error_codes_use_their_own_61xx_band` 用例，把「在 61xx 段内、互不重复、不与 6001–6099 重叠」三条一起钉住——加错一个码，测试立刻红。

| 码 | 名 | 含义 | 用户可见文案 |
|---|---|---|---|
| 6101 | `PLUGIN_NOT_FOUND` | 插件未安装/未加载 | 插件不存在或未加载 |
| 6102 | `PLUGIN_CRASHED` | 进程不在，或刚崩溃 | 插件已崩溃，工具已下架 |
| 6103 | `PLUGIN_CAPABILITY_DENIED` | 能力未授予 | 插件未获得该能力 |
| 6104 | `PLUGIN_API_MISMATCH` | `pluginApi` 不兼容 | 插件与当前版本不兼容 |
| 6105 | `PLUGIN_TIMEOUT` | 调用超时 | 插件响应超时 |
| 6106 | `PLUGIN_PROTOCOL_VIOLATION` | 帧非法 / 方法越权 / 握手不一致 | 插件违反协议，已停止 |
| 6107 | `PLUGIN_MANIFEST_INVALID` | 清单非法（带 `details[]`） | 插件包不合法 |
| 6108 | `PLUGIN_TOOL_CONFLICT` | 工具名冲突 | 工具名与已有工具冲突 |
| 6109 | `PLUGIN_QUOTA_EXCEEDED` | 单次调用宿主 API 超配额 | 插件调用过于频繁，本次已中止 |

`6102` 与 `6101` 必须分开。写成同一个码，模型侧无法区分"这个工具不存在（别编了）"和"插件刚炸了（等它重启）"，会反复重试同一个不存在的工具。demo 里为此专门改过一次：工具已下架但插件进程还在重启时返回 6102 而非 6101。

### 6.7 版本协商

```
宿主 pluginApi = 1.0
插件 pluginApi = 1.x  → 兼容（宿主 minor ≥ 插件 minor 时全功能，否则降级）
插件 pluginApi = 2.x  → 拒载 6104
```

minor 降级的含义：宿主 1.0 遇到声明 1.1 的插件，允许装载但把 `host/*` 里 1.1 新增的方法返回 `-32601`（方法不存在），插件应自行降级。1.0 冻结后的承诺是**只加不删、不加必填字段**。

## 7. 宿主 API

### 7.1 能力矩阵

| 能力 | 覆盖方法 | 默认 | 审批粒度 |
|---|---|---|---|
| `fs.read` | `host/fs.read`、`host/fs.list`、`host/fs.stat` | 授予后免逐次审批 | 无（工作区只读是基线） |
| `fs.write` | `host/fs.write` | 需逐次审批 | 按文件（`scope_key = 规范化路径`） |
| `search` | `host/search.content` | 授予后免逐次审批 | 无 |
| `workspace.info` | `host/workspace.info` | 跟随 `fs.read` | 无 |
| `net.fetch` | `host/net.fetch` | 默认不提供，v1 无实现 | 按域名（预留） |
| `llm.chat` | `host/llm.chat` | 默认不提供，v1 无实现 | 按 provider（预留） |
| `shell.exec` | —— | **不存在**，清单里出现即拒载 | —— |

`fs.read` 免审批是一个需要论证的选择：它的风险是"插件把工作区代码读走"。但插件本来就在用户机器上跑，真要 exfiltrate 需要网络能力，而网络能力单独管（`net.fetch`）。在这个前提下，工作区只读的边际风险远小于让用户每读一个文件点一次确认的体验代价。这条成立的前提是 **`net.fetch` 默认不给**，两者是一组，不能拆开看。

### 7.2 文件原语的语义

| 方法 | 参数 | 关键约束 |
|---|---|---|
| `host/fs.read` | `{path, maxBytes?}` | 相对路径；默认上限 64 KB，超出截断并标记 |
| `host/fs.write` | `{path, content, encoding?}` | 双闸门：先过路径闸门，再过审批；先写临时文件再 rename（掉电不留半个文件） |
| `host/fs.list` | `{path}` | **单层**，返回 `[{name, dir, size}]`；不递归 |
| `host/fs.stat` | `{path}` | `{size, mtime, dir}` |

`fs.list` 不递归是刻意的。递归遍历的策略（跳过 `node_modules`、深度上限、符号链接跟随）属于插件业务，宿主内置一套就会和插件期望打架。代价是往返次数，用 §8.4 的配额兜住。

### 7.3 长任务

`host/progress` 允许插件在 30 s 超时内报告进度：

```json
{"method":"host/progress","params":{"token":"42","percent":30,"message":"扫描 src"}}
```

宿主转成 `plugin.progress` 事件推给外壳。**进度不延长超时**——超时是硬墙，否则一个卡死的插件能把 Core 的等待拖到无限。

## 8. 安全模型

### 8.1 闸门顺序

顺序不可交换，每一步失败的错误码不同，顺序错了错误信息就会指错原因。

```
plugin.call
   │
   ├─ ① 状态闸门   插件存在？状态 ready？        6101 / 6102
   ├─ ② 归属闸门   方法属于该插件？               6106
   ├─ ③ 能力闸门   host/* 所需能力已授予？        6103
   ├─ ④ 路径闸门   相对路径、无 ..、非敏感段？     1002 / 1003
   ├─ ⑤ 审批闸门   risk=write 且未 always？       3001
   └─ ⑥ 配额闸门   单次调用宿主 API ≤ 200 次？    6109
```

③ 在 ⑥ 之前有原因：先判"有没有资格"，再判"用得多不多"。反过来的话，一个没授权的插件会先撞配额，用户看到"调用过于频繁"而不是"未授权"——排查方向直接被带偏。

### 8.2 威胁模型

| # | 威胁 | 对策 | demo 验证 |
|---|---|---|---|
| T1 | 插件读写工作区外文件 | 只接受相对路径；`..` 拒绝；绝对路径拒绝；规范化后必须落在根内 | 场景 07 |
| T2 | 读 `.git/.ssh/.env` 等密钥 | 敏感段硬拒绝（`.git`、`.ssh`、`.aws`、`.kube`），读与写都拒 | 场景 07（`.git/config` → 1003） |
| T3 | 死循环/内存炸弹拖垮 Core | 帧上限 + 超时 + 宿主 API 配额 + 重启上限 | 场景 09 |
| T4 | 插件伪造宿主事件/冒充别的插件 | 插件只能发 `log/progress`；事件由宿主盖 `pluginId`；`plugin.call` 校验 `plugin_id` 归属 | 场景 08（越权方法被拒） |
| T5 | 升级时偷偷扩权 | `capabilities` 新增即回退 `needs_grant` | 未覆盖（v1 待补） |
| T6 | 插件描述里藏提示注入 | 工具描述落库时去控制字符；模型侧标注来源；`plugin.<id>.*` 前缀让来源可辨 | 部分 |
| T7 | 插件返回值伪造工具调用 | 返回值只作 tool result 文本回灌，**不解析为控制指令** | 设计约束，未做自动化测试 |
| T8 | 崩溃循环刷日志 | 3 次重启后停止，状态 `crashed` 等人工处理 | 场景 11 |

T7 值得展开：如果插件返回 `{"tool_calls":[{"name":"run_command","arguments":{"cmd":"rm -rf"}}]}`，宿主**绝不能**把它当成"插件要求执行某工具"。插件只能返回文本/结构化数据，任何执行都必须回到模型 → 审批这条正常链路。这条一旦破了，插件就等于拿到了任意命令执行。

### 8.3 审计

每次 `host/*` 调用落一行，字段固定：

```json
{"ts":"...","pluginId":"demo-hello","action":"fs.write","target":"docs/plugin-note.md","decision":"allow","callId":"call-..."}
```

`quota_exceeded`、`deny`、`approve`、`reject` 都单独记。审计由宿主写，插件无法删改（它没有写审计的 API）。demo 跑完 12 个场景共 211 行审计，其中 200 行来自配额探针——这正好说明配额探针本身也要被审计，否则"打爆配额"这件事在日志里是隐形的。

审计量是个真实问题：`repo_stats` 一次调用产生 4 行，大仓库遍历可能上百行。v1 先全记（审计优先于存储成本），M8 之后再加按插件聚合的滚动归档。

### 8.4 资源配额

| 项 | 值 | 依据 |
|---|---|---|
| 单帧 | 1 MiB | 单行超出即判协议违规 |
| 单次工具结果 | 64 KB | 与 `run_command` 的 `MAX_STREAM_BYTES` 对齐 |
| 单次调用超时 | 30 s（可配至 120 s） | 与命令执行默认值一致 |
| 单次调用宿主 API | 200 次 | 够扫数千文件，不足以打死 IPC 线程 |
| 自动重启 | 3 次 | 崩溃循环的止损线 |
| 并发加载插件 | 8 个 | 每个插件一个进程，Node 进程约 30-50 MB |

进程级限制（内存/CPU）应在 Rust 侧用 OS 能力做：Windows 上用 **Job Object**（`JOB_OBJECT_LIMIT_PROCESS_MEMORY` + `KILL_ON_JOB_CLOSE`），Linux 用 cgroup。**`KILL_ON_JOB_CLOSE` 是必须的**——Core 崩溃时，插件子进程必须跟着死，否则会留下孤儿进程占着文件句柄。

### 8.5 输出污染与提示注入

两条规则：

1. **结果只作数据**。插件结果回灌给模型时是 tool result 文本，不参与任何控制流解析。
2. **来源标注**。工具名强制 `plugin.<id>.<name>`，模型在上下文里看到名字就知道这是第三方提供的。工具描述在注入 system prompt 时加一行 `来源：插件 <id>（第三方，未经审核）`。

第 2 条防不住决心攻击，但能让模型在被诱导时至少有信号可用，也让用户在审批卡片上看得见来源。完整防护需要评测集，不在 v1 范围。

## 9. 内核接线

详细到行级的清单见 [`demo-plugin-system/crates-sketch/protocol_patch.md`](../demo-plugin-system/crates-sketch/protocol_patch.md)，这里只说结构和顺序。

| 位置 | 改动 | 风险 |
|---|---|---|
| `protocol/src/methods.rs` | 加 10 个 `plugin.*` 常量 + 进 `IMPLEMENTED` | 能力清单 46 → 56 |
| `protocol/src/error.rs` | 6xxx 段 9 个码 + `is_plugin_error()` | 无 |
| `core/src/dispatch.rs` | 加 10 个分支（穷举，无动态派发） | 分支与常量必须同提交 |
| `core/src/state.rs` | `plugins: Arc<PluginHost>` + 退出时 `shutdown()` | 漏 shutdown 会留孤儿进程 |
| `core/src/tools/registry.rs` | `with_tool` 注入 `PluginTool` | 冲突返回 6108，不 panic |
| `main/src/policy.ts` | 白名单加 10 项，`plugin.call` 额外校验 `plugin_id` | 两道防线不冗余 |
| `shared-types` | `PluginSummary` / `PluginState` / `PluginToolSummary` | 不把 manifest 原文给渲染端 |

**方法名进表和 dispatch 分支必须同一次提交**。分两次提交的中间态是：`core.hello` 上报了一个调不通的方法。这违反"能力不虚报"，而且这种 bug 只在特定调用路径下暴露，最难排查。

## 10. Agent 集成

### 10.1 工具注入

```rust
for tool in plugin.tools() {
    registry.with_tool(Box::new(PluginTool::new(plugin.id(), tool.clone())))?;
}
```

`PluginTool` 实现现有 `Tool` trait，`name()` 返回 `plugin.<id>.<name>`。前缀不是装饰：它保证 `plugin.` 命名空间与核心工具天然不撞，也让冲突错误（6108）只在插件之间发生。

### 10.2 审批映射

插件工具的 `risk` 直接映射到现有 `PermissionGate` 的动作：

| 插件声明 | 闸门动作 | `scope_key` |
|---|---|---|
| `read` | `allow`（免询问，仍审计） | —— |
| `write` | `ask` | 规范化绝对路径 |
| `exec` | `ask`，且 v1 不允许插件申请 `shell.exec` | —— |

`scope_key` 用规范化后的**绝对路径**而非插件给的相对路径。相对路径是插件可控的（`./a/../b` 与 `b` 是同一个文件），拿它当记忆键，用户"总是允许"的范围会被插件操纵。

### 10.3 结果回灌

- 截断到 64 KB，追加上限标记（与 `run_command` 一致，模型对这段标记有先验）。
- 结果结构与核心工具一致（`content` 字符串），不引入插件自定义结构，避免模型侧出现两套解析路径。

### 10.4 崩溃时模型看到什么

工具下架后，模型若仍发出该工具的调用，返回值必须是 **6102 + 明确文案**（"插件已崩溃，工具已下架"），不能是"未知工具"。前者让模型停止重试并告知用户；后者会让模型以为自己记错了工具名，转而尝试变体名，把一轮对话耗光。

## 11. 可观测性

| 信号 | 去处 | 内容 |
|---|---|---|
| `plugin.log` | 外壳日志面板 | 级别、插件 id、消息；stdout 被污染时取代它 |
| `plugin.state_changed` | 外壳状态栏 | 状态迁移 + 原因（崩溃码、超时、授权不足） |
| `plugin.progress` | 工具调用卡片 | 百分比 + 消息 |
| `tool_audit` | 审计面板 | §8.3 |
| 崩溃计数 / 重启次数 | `plugin.status` | 诊断面板直接展示 |

`plugin.status` 要能回答"为什么这个插件现在是 crashed"：返回 `lastError {code, message, at}` 与 `restarts`。没有这两项，用户只能看到"崩了"，然后去翻日志。

## 12. 失败模式与降级

| 失败 | 表现 | 处理 |
|---|---|---|
| 插件入口不存在 / 语法错 | spawn 后立即退出 | 6102 + `lastError`，不自动重启（这是确定性错误，重试无意义） |
| 握手超时 | 无响应 | 6105，杀进程，可重启 |
| 握手工具集合不一致 | 多报/少报 | 6106，杀进程，不重启（需要作者修） |
| 调用中超时 | 30 s 无响应 | 6105，**杀进程**（挂住的进程可能持有半写文件） |
| stdout 出现非协议行 | 帧解析失败 | 6106，杀进程 + 保留最后 20 行原始输出供诊断 |
| 插件 OOM / 段错误 | 进程消失 | `plugin.crashed`，工具下架，≤3 次重启 |
| 磁盘写失败 | `fs.write` 错误 | 透传 2xxx 错误，不自动重试 |
| 工作区根变更 | `workspace.info` 变化 | 广播 `workspace.changed`，插件自行重算；宿主不清缓存 |

**超时即杀进程**这一条要单独说。不杀的话，一个超时的调用可能仍在后台写文件，而宿主已经把错误返回给模型，模型可能基于"失败"做出后续决策——此时磁盘上的状态和模型的认知已经不一致。

| 阶段 | 内容 | 验收判定 |
|---|---|---|
| **P0** 协议骨架 | 10 个方法名 + 9 个错误码（`6101`–`6109`）+ dispatch 空分支（全部返回 6101） | `cargo test -p protocol` 通过；`core.hello` 能力清单 71 项且逐项可调（空分支返回 6101 也算可调）；`pnpm typecheck` 零漂移 |

| **P2** 装载与握手 | `load` / `unload` / `reload` + 子进程监管 | 握手不一致拒载；崩溃后工具下架；Core 退出无孤儿进程（任务管理器核对） |
| **P3** 工具注入 | `PluginTool` + ToolRegistry + 审批映射 | 模型可调用 `plugin.*` 工具；`risk=write` 触发审批；拒绝后无副作用 |
| **P4** 能力与审计 | `grant` / `revoke` + 审计落库 | 撤销能力后调用返回 6103；审计行数与宿主调用数一致 |
| **P5** 命令与事件 | `commands` 进命令面板；事件订阅 | 未订阅插件收不到事件；命令执行走同一套闸门 |

落地进度：**P0 / P1 / P2 已完成（2026-10-23，`9b5d9fa` / `0a73bf7` / `eaaf425` / `7259d96` / `23ff19e` / `1b06006` / `4e44f0a`）**。P1 两条判定均实测达成，见 [`16-插件-P1-验收报告.md`](./16-插件-P1-验收报告.md)；P2 三条判定（握手不一致拒载、崩溃后工具下架、Core 退出无孤儿）同样实测达成，见 [`17-插件-P2-验收报告.md`](./17-插件-P2-验收报告.md)。P2 实现口径补充：崩溃后**非确定性退出自动重启、同一次装载上限 3 次**（到顶停在 `crashed` 并写明原因，确定性失败如握手被拒 / 协议违规一次都不重试），这是本节原文未写、由场景 11 要求推出并已补测试的行为；`Qualification` 的「任务管理器核对」改为自动化用例（`taskkill /F` 强杀内核 + 插件进程存活断言），比人工核对更严格。已知口径偏差一处：`PluginInstallParams.path` 的注释写「目录或 `.zip`」，P1 实现只读目录包，zip 支持与注释订正留给后续切片。

落地进度续：**P3 已完成（2026-10-24，`dc7cde6` + 工具注入提交）**。P3 三条判定（模型可调用插件工具、`risk=write` 触发审批、拒绝后无副作用）均实测达成，见 [`19-插件-P3-验收报告.md`](./19-插件-P3-验收报告.md)。实现口径补充三点：① 插件工具从 **agent 注册表**进（`plugin__<id>__<tool>`），不经 `plugin.call`，因此 `plugin.call` 仍是 `6101` 空分支、能力清单仍是 71 项；② `risk=read` 的免问走 `PermissionGate` 新增的**运行期只读集合** `extra_read`，而不是往编译期常量 `READ_TOOLS` 里塞——且只读直通不免路径校验，越界路径照旧 `1002`；③ **审批被拒不计入 `steps`**（runner 既有口径，闸门在 `steps += 1` 之前），被拒的调用只回一条可回灌的工具错误。已知限制：`risk` 是插件握手自报的「声明信任」，内核无法核对插件真实行为；同一次运行内工具表是快照，中途装载的插件下次运行才生效。

P3 与 P4 **必须同版本发布**。P3 之后工具已能被模型调用，但审计还没接上——这段窗口里插件的写操作是裸奔的。

P2 要求的 `kill -9` 集成测试**已补**：`crates/core/tests/plugin_flow.rs::forced_kill_of_core_leaves_no_orphan_plugin_process`，用 `taskkill /F`（不加 `/T`，否则测到的是进程树连坐而非作业对象）强杀内核，断言插件进程 10 s 内消失且未收到 `plugin/shutdown`；用例内插件挂心跳保活，排除「读 stdin EOF 自行退出」造成的假绿。

## 14. 验证原型

`demo-plugin-system/` 是 Node 零依赖实现，跑 `node run-demo.mjs` 输出 12/12。它验证的是**状态机与闸门顺序**，不是内核接线。

| 场景 | 验证内容 |
|---|---|
| 01 | 清单 6 类错误一次报全，零进程启动 |
| 02 | 未授权 → 6103，零进程启动 |
| 03 | 握手注册 6 个工具，命名带前缀 |
| 04 | `read` 工具免审批，结果回灌 |
| 05 | `write` 工具审批通过后落盘（169 字节，逐字节核对） |
| 06 | 审批拒绝 → 3001，文件未创建 |
| 07 | `..` → 1002，`.git/config` → 1003，绝对路径 → 1002 |
| 08 | 未申请 `net.fetch` → 6103 |
| 09 | 第 201 次宿主调用 → 6109 |
| 10 | 事件只投给声明订阅者 |
| 11 | 崩溃 → 工具立即下架 → 调用 6102 → 重启恢复 |
| 12 | 卸载 → 工具清零，进程退出 |

与 Rust 骨架（`crates-sketch/`）的对应关系写在 `crates-sketch/README.md`。骨架**刻意不可编译**：闸门顺序和状态机是设计约束的载体，行为验证由 demo 负责。把两件事混在一个"能跑的骨架"里，会让人以为接线已完成。

## 15. 风险与未决

| # | 问题 | 现状 | 建议 |
|---|---|---|---|
| Q1 | 审计量随插件调用线性增长 | 全量落库 | M8 后按插件 + 天聚合归档，原始行保留 7 天 |
| Q2 | Windows 子进程清理依赖 Job Object，需在 Rust 侧实现 | **已实现**（P2，`crates/plugin/src/loader.rs`：`KILL_ON_JOB_CLOSE`） | kill -9 集成测试已补：`forced_kill_of_core_leaves_no_orphan_plugin_process` |
| Q3 | 插件 SDK 只有 Node 等价物 | demo 手写协议 | 抽 `@ai-ide/plugin-sdk`，把帧编解码与 `host/*` 客户端封装掉；协议不变 |
| Q4 | Python 插件需要运行时 | 只 spawn 可执行文件 | 让插件自带解释器路径或依赖系统 Python，宿主不内嵌 |
| Q5 | 插件市场与签名 | 不做 | v2 再议；签名之前，安装等同于"运行任意代码"，UI 必须明示 |
| Q6 | UI 贡献点 | 协议位预留 | v2 走 Core → Main → Renderer，Renderer 侧只接受声明式（JSON 描述），不接受插件 JS 在渲染进程执行 |
| Q7 | 提示注入防护 | 只有来源标注 | 需要评测集，单独排期 |
| Q8 | 插件间通信 | v1 禁止 | 需要时通过宿主中转事件，不让插件直连（否则权限模型失效） |

Q2 与 Q3 是 P2 的硬前置。Q5 在签名之前，产品文案不能说"安全的插件系统"，只能说"有闸门的插件运行环境"——这个区别在出事故时是决定性的。

## 附录 B · 与现有文档的口径差异

| 现有文档 | 本文口径 | 说明 |
|---|---|---|
| 02 §8 双闸门 | 三主体（Renderer / 插件 / Core） | 插件作为第四类主体进入信任模型，Main 不参与插件调用裁决（插件不走 IPC 白名单） |
| 02 §8 要点 4 审计落 `tool_audit` | 插件 `host/*` 调用同样落该表，附 `pluginId` | 复用现有表，不新建 |
| 03 能力清单 46 项 | 加 10 项 → 56 项 | 仅在插件接线后成立 |
| 04 工具集 | 加 `plugin.<id>.*` 动态工具 | 工具总数不再静态可数，但命名空间受限 |

最后一行是这次设计引入的唯一一个"动态"：工具集合在运行时可变。它不破坏协议层静态性（方法表仍然固定 56 项），但会破坏"工具列表可静态枚举"这个隐含假设。凡是按工具名做硬编码分支的逻辑（例如 M4 的审批卡片文案映射），都要预留未知工具的兜底路径。
