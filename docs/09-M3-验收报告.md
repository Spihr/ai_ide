## 四、M3 期间缺陷复盘（2 条）

### 1. 门禁 flaky：假上游的连接竞争（`c7549ca`）

- **现象**：`llm_flow` 偶发失败，每次症状一致——客户端报 `connection closed before message completed` 或 os error `10053`，内核据此如实报网络错误 `2005`（`llm.error`）。失败用例在「模型清单_转发上游结果」「流式对话_端到端」「取消只终结本流」「上下文引用」之间随机漂移，跑得快时更容易出现。
- **根因**：假上游用非阻塞监听 + 轮询 `accept`，而 Windows 上 `accept` 出的连接会**继承监听套接字的非阻塞状态**。`serve` 里的首次 `read` 只要请求还没到，立刻以 `WouldBlock(10035)` 失败并关掉连接——纯时序竞争。
- **修复**：连接进入 `serve` 时显式 `set_nonblocking(false)`，把非阻塞明确限定在 `accept` 轮询上；`accept` 循环不再因单条排队连接异常（`WouldBlock` / `Interrupted` / `TimedOut` / `ConnectionAborted`）整体退出。
- **验证**：修复前 25 轮 20 通过 / 5 失败；修复后 30 轮，另加 10 轮开 trace 交叉验证，40/40 全绿，12 例全过；`pnpm verify:m2` 退出码 0。
- **边界**：这是测试脚手架缺陷，不是内核缺陷（内核在上游掐断处报 `llm.error` 属正确行为）。**未**用重试、加长 sleep、放宽断言或吞错来掩盖。
- **顺带补齐可观测性**（默认关闭，不改正常路径）：`AI_IDE_TEST_UPSTREAM_TRACE`、`AI_IDE_TEST_CORE_LOG`、reqwest 错误补 `source` 链。

### 2. 协议文档与实现不一致（M2 遗留的起点，M3 内收敛）

- **现象（M2 遗留）**：`docs/03` §2.4 的 `llm.chat_stream` 示例含 `context` 与 `compress{strategy,budget_tokens}`，而实现的 `LlmChatStreamParams` 无 `context` 字段；`llm.count_tokens` 文档写 `{model_ref, texts[]}`，实现是 `{model_ref, messages[]}`。
- **处理**：M3 三次提交同步 `docs/03`（`0430773` 30 行、`d787f94` 13 行、`7cda67c` 2 行），把注入位置与顺序、来源标注、选区口径（行号优先）、失效与截断是标注、越界是硬失败、预算语义与两策略分流、计数口径分流全部写成协议正式条款（见 §2.4）。
- **顺带纠正**：`antidisestablishmentarianism` 实测为 6 而非初稿凭记忆写的 5，已按**实测值**锚定并注明来源，未调松断言。

## 五、如实记录的三处限制

### ① 估算口径的实测偏差区间（远超 3%）

估算器（CJK 1 字 1 token / ASCII 4 字 1 token）与官方词表的实测偏差：

| 词表 | 逐向量偏差（估算 vs 官方） | 区间 |
| --- | --- | --- |
| `o200k_base` | −34.6% / −13.6% / +27.3% / +18.2% / −31.2% | **−34.6% ~ +27.3%** |
| `cl100k_base` | −34.6% / −9.5% / −6.7% / −4.9% / −38.9% | **−38.9% ~ −4.9%**（最差 **−38.9%**） |

- 估算器**只用于未识别模型族的回落路径**（`exact:false`），且 `note` 会带出口径说明供 UI 标注；已识别族一律走真实分词器。
- 引用预算裁剪走的是估算口径，因此预算判定带同量级不确定性（预算满足的是估算值上限，不是精确 token 上限）。
- 该偏差**不打断言**、只打印实测值并如实记录：把估算器调到「看起来达标」才是谎报。
- 复现：`cargo test -p ai-ide-llm 估算口径_实测偏差如实记录 -- --nocapture`。

### ② `summarize` 是离线抽取式摘要，该定义为本次自定

- 原协议（`docs/03` §2.4）**只记了占位语义**（内核按 `truncate` 处理），没有给 `summarize` 的行为定义；本次按最小可用定义落地并在协议文档中固化：保留段头（来源标注）与段尾（闭合标签），中间只留头尾若干行，以 `<!-- 摘要：原文正文共 N 行，此处省略中间 M 行 -->` 交代省略规模；骨架放不下时**整段省略**，不留残缺块。
- 该摘要**只用本地字符串处理**：不调用模型、不读密钥、不联网，因此断网或未配 Provider 时照常可用，门禁不依赖外部服务；代价是它**不产生语义总结**，只是「结构完整的抽取」。
- `docs/05` 原计划里的 5 级压缩策略，本次只落地 2 级（`truncate` / 离线 `summarize`）；**模型摘要**（`docs/04` §2.3 第 4 级）属后续切片。

### ③ tiktoken 精确口径未对真实厂商接口做端到端比对

- 现有证据仅两层：**算法同源**（tiktoken-rs 的 `o200k_base` / `cl100k_base` 词表，进程内只解析一次、随二进制内嵌、不联网）+ **官方示例向量交叉校验**（tiktoken 官方 README 的 `hello world` → 2、`tiktoken is great!` → 6）。
- **未**对真实厂商 `/chat/completions` 返回的 `usage.prompt_tokens` 做端到端核对（M3 验收时无可用凭据；M4 阶段已用真实网关跑通对话链路并采集到上游用量，但未与本地计数逐例比对）。厂商侧还有额外的消息模板开销，本地计数与上游 `usage` 允许有差——**真实用量以上游 `llm.usage` 为准**。
- 因此本报告只能声称「对已接词表的模型族，本地计数与官方分词器一致」，不能声称「与厂商计费口径一致」。
